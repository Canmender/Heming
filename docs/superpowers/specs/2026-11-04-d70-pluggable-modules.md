# d.70 内置能力模块可插拔化（幕僚 / 信息中枢 / 自动化）

- 分支：`feat/d70-pluggable-modules`（从 `d.68.2.32.0` 的 `feat/d69-ux-round` 拉出）
- 版本：`d.69.2.32.0`（特性位 +1：新增「内置能力模块」装配模型与插件区模块页）
- 目标：把原来写死在导航里的三个内置页——**幕僚 / 信息中枢 / 自动化**——改成插件式的
  **可插拔能力模块**：在插件区统一查看版本、贡献、依赖与本机数据，用开关启用/停用；
  停用后入口、页面、首页卡、后台常驻任务、模型工具注入与（信息中枢）本机边车一起下线。

---

## 1. 为什么不是「第三方 plugin.json 贡献页面」

现有 `plugin.json`（v3）是**纯声明式能力包**：技能 / 远程 MCP / 命令 / 工具束，
安装不执行任何随包代码（红线）。如果让它贡献 React 页面，等于打开「安装即执行任意 UI 代码」，
与既有的插件信任模型（内容指纹 + TOFU + 逐工具授权）不相容。

因此本轮的做法是：

> **同一套插件区的展示与启用语义，两组注册表。**
> - 第三方能力 → `heming.plugins.v1`（装/卸/更新，贡献技能与服务）；
> - 内置能力模块 → `heming.modules.v1`（只有启用/停用，代码随应用发布）。
>
> 插件区新增「模块」Tab，用与插件卡同样的字段（id / 版本 / 描述 / 贡献 / 边界）展示这三个模块。
> 页面贡献能力**只对内置模块开放**，第三方页面贡献需要另立「沙箱化插件 UI」规格，本轮明确不做。

## 2. 模型与存储

`packages/web/src/lib/modules/`

| 文件 | 职责 |
|---|---|
| `registry.ts` | 三个模块的声明式描述：`id / name / version / description / page / contributions / requires / dataKeys / disableNote`；`moduleForPage()` 供导航/路由反查 |
| `store.ts` | 启用状态 `heming.modules.v1`（本机、不上云、不导出）；`normalizeModuleState` 坏值回落默认；`isModuleEffective` 处理依赖；`missingRequirements` 给卡片说明；zustand store + `isModuleOn()` 给非 React 代码 |
| `nav.ts` | 纯函数接线：`isPageAvailable` / `filterNavOrder` / `filterPalettePages` / `fallbackPage`（导航、命令面板、路由、设置导航顺序、跳转守卫共用一份判据） |
| `components/plugins/ModulesView.tsx` | 插件区「模块」Tab 的卡片与开关；依赖未满足时显示原因、禁用「打开页面」 |

**默认全开**：升级后行为与 d.68.2.32.0 完全一致；键缺失/坏 JSON/单字段坏值都回落「启用」，
避免一次坏数据把模块锁死。未知模块 id 直接丢弃（未来下线的模块不会留下幽灵开关）。

**依赖**：`automations` 依赖 `infohub`。依赖停用时，自动化的**开关仍保留、但实际不生效**
（卡片显示「依赖未启用」），依赖重新启用后自动恢复——不出现「开关是开的、却什么都不工作」的静默状态。
不采用「停信息中枢就顺手改自动化的开关」：那会让用户分不清哪个状态是自己选的。

**停用不删数据**：`dataKeys` 只做展示；停用只撤入口与运行时挂载，重新启用即恢复。
所有业务键（`heming.staff.v1`、`heming.automations.v1`、归档配置/数据库）原样保留。

## 3. 接线矩阵（启用状态 → 实际行为）

| 位置 | 停用后的行为 | 实现 |
|---|---|---|
| 导航轨 | 模块页按钮撤下；重新启用按 `navOrder` 原位置回来 | `NavRail` 读 store + `filterNavOrder`；模块页显示名以注册表为准（与卡片同源） |
| 页面路由 | 当前页不可用时回主页（通知/桌宠/旧链接指向已停用页也适用） | `App` 计算 `currentPage` + `useEffect` 重定向 |
| 首页 | 幕僚卡 / 本机归档卡下线 | `HomePage` 条件渲染 |
| 命令面板 | 页面跳转、最近使用、插件命令目标都不再出现停用页 | `CommandPalette` 传 `filterPalettePages` 结果 |
| 设置区导航顺序 | 隐藏停用页；上/下移只在可见项之间交换（隐藏页占位不动） | `SettingsPage.NavigationSection` 过滤 + 合并回写 |
| 后台常驻 | 幕僚巡检、自动化调度不再挂载 | `App` 把 `isModuleEffective(...)` 传给 `useStaffLoop` / `useAutomationScheduler` |
| 模型工具 | `infohub_*` 工具不再注入 | `buildInfohubToolsIfConnected()` 先判模块 |
| 信息中枢边车 | 已连接的本机进程在停用后释放（不删归档，不自动拉起） | `App` 监听停用 → `useInfohubStore.disconnect()` |
| 跨模块入口 | 幕僚「看日程」、信息中枢「定时 / 保存为定时任务 / 定时重扫」在目标模块停用时禁用并给原因 | `StaffPage` / `InfohubPage` |
| 跳转兜底 | `openInfohub` / `openAutomations` 在模块停用时不再切页（按钮层已禁用，这里兜通知/旧链接） | `store/ui.ts` |

明确不变：HITL 判定、E2E、数据出设备边界、插件安装/信任模型、导航快捷键（三个模块页本来就不占数字键）。

## 4. 用户可见入口

插件区 → **模块** Tab（与「插件 / 技能 / 工具 / MCP 服务」并列）：

- 卡片：图标、名称、`内置` 徽标、版本、描述、`已启用/已停用` 状态与开关；
- 贡献：导航入口 + 页面 / 首页卡片 / 后台巡检或调度 / 模型工具前缀；
- 本机数据：列出该模块的存储键，写明「停用不删除」；
- 依赖：需要哪个模块，未满足时高亮「当前未满足」；
- 停用后会发生什么（一句话）；「打开页面」按钮（不可用时禁用并说明「依赖项启用后自动恢复」）；
- 「全部恢复启用」一键回到默认。

## 5. 测试与验证

单测（web 232 文件 / 3450 例 → 本轮新增见 CHANGELOG）：

- `lib/modules/store.test.ts`：默认全开、坏值/未知 id 回落、依赖语义、落盘/重置/幂等；
- `lib/modules/nav.test.ts`：导航过滤、依赖联动、命令面板目录过滤、路由落点、注册表与页面目录同源；
- `components/plugins/ModulesView.test.tsx`：三卡渲染、开关、依赖未满足时禁用、全部恢复；
- `components/PluginsPage.test.tsx`：模块 Tab 可见且能切换；
- `NavRail.test.tsx` / `HomePage.test.tsx`：停用后入口/卡片消失、默认全在；
- `lib/infohub/tools.test.ts`：模块停用后不注入 `infohub_*`；
- 既有 3427 例全部保持绿（默认全开 = 行为不变，是这轮的兼容底线）。

真实浏览器（headless Edge + CDP，脚本只在本机 `.tmp/d70/`、不入库）：

- 默认 9 个导航项 + 首页幕僚/归档卡；
- 停信息中枢：导航「信息中枢」「自动化」同时撤下（依赖）、首页归档卡消失、命令面板搜「信息」无该页、
  设置区导航顺序只剩 7 项、自动化卡显示「依赖未启用」且「打开页面」禁用；
- 停幕僚：导航撤下、首页幕僚卡消失；
- 全部恢复：9 个导航项按原顺序回来、三个开关回到启用；
- 停自动化后刷新：导航仍无自动化，`heming.modules.v1` 为
  `{"enabled":{"staff":true,"infohub":true,"automations":false}}`（本机持久化生效）。

## 6. 明确不做 / 下一步

1. **第三方插件贡献页面**：需要沙箱化 UI 规格（iframe / 权限声明 / CSP / 页面路由白名单），本轮不做。
2. **模块卸载（连带删数据）**：只提供停用；删除本机数据另有各模块自己的清理入口，不把两件事绑在一起。
3. **模块级权限声明**（如信息中枢声明读取归档路径）：当前卡片只声明数据键与依赖，权限仍由各页面自己的 UI 约束。
4. **模块顺序自定义**：沿用现有 `navOrder`，停用不改变其余页顺序；未提供「模块分组」。
5. **停用后的设置入口**：幕僚/信息中枢的设置在各自主页内，模块停用时一并不可达；若用户要清数据，
   启用 → 打开页面 → 使用页面里的清理入口（或设置区已有的本机存储卡）。后续可评估在模块卡上加「清理数据」。
