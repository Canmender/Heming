# 记忆个性化权重（d.28.1.7.0）

日期：2026-10-22
状态：已实现
相关：`docs/superpowers/specs/2026-10-22-memory-recall-observability.md`（d.27 归因链路）、`docs/superpowers/specs/2026-10-21-memory-recall-ranking.md`（打分与多样性重排）、`docs/HANDOFF.md` §5 #4

## 1. 问题

d.27 把归因链路做出来了：每次生成留下注入清单，收尾时用字符串级词重合判出「疑似引用」。
但**这些数字一个都没回到排序里**。于是有三个缺口：

1. **归因白算**。同一条记忆被引用十次和从没被引用，下次召回的分数一模一样。用户能看到「这条被用到了」，
   却看不到系统因此变得更好——可观测性没有兑换成任何行为差异，功能停在了「显示」这一层。
2. **同等相关度里的先后是随机的**。语义层的命中打分是 `命中词数 / 查询词数 × 衰减 × 置信度`，
   两条同主题族的条目（「部署端口」「部署目录」）命中数一样、写入时间一样、置信度一样，
   谁进 top5 完全由数组顺序决定。真实体感是「同一件事每次带的两条顺序还会变」，而系统其实有能力知道哪条更有用。
3. **冷记忆没有被看见的机会**。注入了六七次、一次都没被引用过的条目，在预算里始终占着一行。
   用户想清掉它，只能逐条翻几十张卡片凭感觉判断。

最容易被带偏的解法是「再问一次模型这次用了哪条记忆」，或者让模型给每条记忆打个相关性分。
两者都被排除：那是第二次 LLM 成本，且答案不可复现（同一份注入这次说用了、下次说没用），
用户在记忆区看到的「加权 ×1.17」就重新变回玄学——**这一轮的前提仍是确定性规则**（HANDOFF §5 #4 原文口径）。

## 2. 决策

### 2.1 权重从「疑似引用」计数来，公式手算得出来

`usage.ts` 的因子只有一个公式：

```
boost = 1 + USAGE_BOOST_MAX × used / (used + USAGE_SMOOTH)     // USAGE_BOOST_MAX = 0.25，USAGE_SMOOTH = 3
```

| used（疑似引用次数） | 乘子 | 说明 |
| --- | --- | --- |
| 0 | ×1 | 不偏不倚，一分不加 |
| 1 | ×1.0625 | 一次引用不足以定功，平滑项把它压低 |
| 3 | ×1.125 | |
| 6 | ×1.1667 | |
| →∞ | <×1.25 | 永远取不到上限 |

两个常数都是有理由的，不是拍的：

- **`USAGE_BOOST_MAX = 0.25`（封顶）**。不封顶的话，几条「常青」记忆会稳定压过一切新条目，
  等于用历史热度锁死预算——新事实永远排不上，记忆系统停止吸收。25% 的量级取自
  「同等相关度下改判先后足够，但跨一档质量差（90 天半衰期 → 0.5 倍）改不动」，
  这条正好有用例钉住（`recall.test.ts` 的「提权封顶改不了明显的质量差」）。
- **`USAGE_SMOOTH = 3`**。`used/(used+3)` 是拉普拉斯式饱和：1 次引用只给 1/4 的最大加成，
  避免「偶然撞上一次词重合」就把这条记忆抬成常驻冠军。

**只提权，不降权**。从没被引用的记忆一分不扣。降权的语义是「系统判定这条对用户没用」，
而我们的判据只是词重合，本来就偏保守（工具调用里用了但正文没复述的不算，见 §5），
拿一个漏判率未知的指标去扣分，等于让噪声累积成惩罚。冷记忆只进清单给人看、给人删。

### 2.2 账本单独一个键，而不是从召回日志现算

`heming.memory.usage.v1`：条目 id → `{ injected, used, lastAt }`，由 `RecallRecorder.settle` 每轮累加一档。

为什么不直接 `buildUsageStats(recallLog.list())`（少一个键、少一处写入）：
召回日志是**环形 40 档 / 256KB**，聊得多一天就滚掉了。权重若挂在日志上，
用户会看到「上周还挺准的匹配，这周莫名其妙变差了」，而真实原因（旧档被裁了）与他无关——
这是把自己实现的存储上限暴露成用户可感知的退化。**账本按条目 id 累加，滚动窗口不影响它。**

三条写入规则（`UsageLedger.apply`）：

- **一档只计一次**：同一 id 在这一档里出现几回都只加一（一轮注入不该把计数翻倍）。
- **跳过工作层与 `focus`**：那几行就是刚才的对话，回答必然复述其中的词，计数只有噪声——与 `attribution.ts` 同一口径。
- **`used` 只能落在本档注入过的条目上**，且水合时被夹在 `[0, injected]` 内（脏数据不放大权重）。

容量与失效：条目数超 `USAGE_LEDGER_MAX = 400` 按 `lastAt` 最旧先丢；字节护栏 64KB（比日志还小一档，
诊断数据不吃 localStorage 配额）；读到的 JSON 坏了整键回退空表；写失败静默。

**账本与日志同进同退**：`settle` 里只有 `log.record()` 真的落盘（返回非 null）才 `usage.apply(run)`。
否则会出现「卡片上写着加权 ×1.17，但召回记录里查不到任何一次引用的原始档案」——
一个解释不了的数字比没有数字更伤信任（用例：`runRecorder.test.ts` 的落盘失败那条）。

### 2.3 排序侧只接一个方法：`UsageView { boostOf(id) }`

`recallMemory(store, input, usage?)` 第三参数是接口而不是账本实例，缺省 `NEUTRAL_USAGE`。理由：

- **回归护栏必须是可断言的**：不传 usage 时所有乘子为 1，`scores` 与 d.27 **逐字相同**
  （用例直接 deep-equal 两份完整结果）。若 recall 直接依赖 `UsageLedger`，这条只能靠读代码相信。
- 召回不需要知道「为什么是 1.1667」，公式、存储、容量都留在 usage 层。

乘子落点（`recall.ts`）：语义的 pinned 项、语义的命中项、情景的 BM25 项、情景无查询时的兜底排序，四处都乘。
`settle(entry, base)` 把「最终分」与「其中提了多少」分开记录到 `scores` / `boosts`，
多样性重排 `pickDiverse` 用的是乘完之后的分（否则加权只在展示层生效，选了名额也不算）。

**没动的东西**：预算 1200 字符、三层占比、top5/top3/6 名额、时效覆盖、MMR 降权幅度、总开关关闭即零注入。
权重只改「同样相关的两条谁在前」。

### 2.4 旁路字段 `boosts`，与记忆页三处落点

`MemoryObservability` 增一个字段（`format.ts`）：

| 字段 | 含义 | 为什么只收 `>1` |
| --- | --- | --- |
| `boosts` | 条目 id → 个性化乘子 | `×1` 是「其实没加权」，全量铺开会让 UI 出现一片无意义的 1，也会把日志体积白撑大 |

`scores` 已经是乘完的最终值，`boosts` 给的是「其中提了多少」，UI 用它解释「为什么这条排在前面」，不重新参与排序。

记忆页（`MemoryPage.tsx`）三处：

1. **卡片注脚新增一行**（语义卡与情景卡）：`累计注入 6 次 · 疑似引用 6 次 · 个性化加权 ×1.1667`。
   刻意单独成行、接在 d.27 的日期注脚之后——日期说的是「最近一次」，计数说的是「累计」，两个口径挤一行读不懂。
   **没有任何计数时整行不出现**：不显示「×1」。
2. **召回预览每行**带 `· 加权 ×1.1667`；预览调用把账本传进 `recallMemory`，
   与真实生成走同一条路——否则「预览里看到的顺序」和「实际注入的顺序」会是两套。
3. **「长期未被引用」清单**：`isColdUsage` 判据是「注入 ≥ `COLD_MIN_INJECTED`（6）次且 0 次疑似引用」。
   每条带删除按钮，走既有的二次确认弹窗；**没有任何自动淘汰**。
   文案明写「系统不会因为『冷』自动降权或删除它们……也有可能其实被用到了只是正文没复述」。

配套的两个一致性动作：删除记忆 → `recorder.forgetUsage([id])`（不留孤儿计数）；
清除召回记录 → 日志与账本一起清，确认文案写明「个性化加权回到起点」。
后者顺带修了一个真 bug：清除后必须 `bump()`，否则 `usage` 的 memo 停在旧快照上，
卡片继续显示已经清零的权重（用例：`MemoryPage.test.tsx`「清除召回记录把加权账本一起清零」）。

## 3. 隐私边界

- 账本只记**条目 id 与两个整数**，不记查询原文、不记回答原文——那些在召回日志里已有截断留档，各自一份职责。
- 与召回日志同属**本机诊断数据**：不进三层记忆键，**不参与记忆导出/导入**。
  换设备带走的是记下来的事实，不是「这台机器上哪几条常被用到」。
- 零网络调用、零额外模型调用；写失败一律静默，绝不影响发送与流式渲染。

## 4. 测试

新增 30 例：

- `usage.ts` 16 例：因子可手算、单调且封顶、冷判据、一档只计一次、跳过工作层与 `focus`、
  引用必须落在注入过的条目上、跨实例读回同一份计数、坏 JSON 与脏字段回退/夹紧、满容量淘汰最旧、
  `forget` 与 `clear`、`null` 档不动账本。
- `recall.ts` +7 例：不传 usage 与显式 ×1 视图结果逐字相同、同分候选被提权者在前、
  封顶改不动质量差、pinned 也吃乘子、**冷记忆一分不降权（与中性结果 deep-equal）**、情景层同样生效、
  `summarizeInjection` 原样带出乘子。
- `context.ts` +3 例：注入文本里的真实顺序真的换了、条数与层名额一个都没变。
- `MemoryPage.tsx` +4 例：卡片加权注脚（含 `×1.1667` 这个可手算的数字）、预览行标出乘子且冷的没标、
  清除后账本与视图一起归零、删除后账本不留孤儿 id。

断言方向刻意挑过：「不降权」写成与中性结果的**相等**，不是「不小于」；
「一档只计一次」写成 `injected: 1`，不是 `<= 1`。

## 5. 已知边界与后续

- **判据只看最终回答正文**。工具调用里引用了、正文没复述的不算——所以冷清单可能误列，提权可能漏加。
  这是「宁可漏报不误报」的代价，界面一律写「疑似引用」，不写「已使用」。
- **同智能体同一句在两处同时在飞会串档**（`agentId::userText` 配对，d.27 遗留）。串档会把计数记到错误的档上，
  严格化要等钩子带上 streamId。
- **账本记满 400 条按最后一次计入淘汰**。淘汰的是计数不是记忆本身；被清掉计数的记忆退回 ×1，
  然后随着被再次引用重新长回来——这个「失忆」是设计选择，不是漏洞。
- **没有自动淘汰**。下一步若要接，判据不能只有「冷」，至少要叠「低置信 + 长期未更新 + 用户确认」。
- 权重目前对**语义与情景两层**生效；工作层不参与（口径同上）。
- 上限 25%、平滑 3、冷门槛 6 次都是导出的常量，改起来是一行的事，但没有真机反馈前不调。
