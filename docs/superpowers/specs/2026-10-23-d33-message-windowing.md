# d.33 · 消息列表窗口化（P2-2）

- 日期：2026-10-23
- 相关版本：d.32.1.8.0（基线）、本 spec = d.33.1.8.0
- 上游依据：`docs/research/2026-10-22-deep-audit-followup-plan.md` §4 P2-2、§7 分轮表、§8 待拍板项 ④
- 涉及包：`packages/web`

## 0. 这一轮要解决什么

`ChatPage` 的消息区是 `visibleMessages.map(...)` **全量渲染**：会话有 800 条消息就挂 800 个气泡，
每条还带引用卡、回应 chips、图表解析、Markdown。首屏开销随会话长度线性增长，
而 `packages/web/package.json` 里没有任何虚拟列表依赖。

**本轮做「轻量窗口化」**：只渲染最近 N 条，向上滚动时按步长追加更早的消息。
**不引第三方依赖**（计划 §8 已倾向这条）。

## 2. 决策

### 2.1 窗口化在**渲染层**，不动数据层

数据仍全量加载（服务端一次给全，改成分页要动接口、动 E2E 解密链路，代价远大于收益）。
本轮只控制「同时挂多少 DOM 节点」。

**为什么不引 `react-window`/`tanstack-virtual`**：
- 本项目消息行高度**不定**（引用卡、图表、Markdown、附件、语音条），虚拟列表需要
  测量/估算高度，接进来要改每一条消息的渲染容器，回归风险高；
- 轻量窗口化只有几十行，且不改变消息行的 DOM 结构（搜索跳转、`msg-<id>` 锚点、
  多选、回复引用全都照旧）；
- 计划 §8 ④ 已写明「倾向不引第三方依赖」。

### 2.2 窗口参数

- **初始窗口 60 条**（`DEFAULT_WINDOW`）：一屏约 8–12 条，60 条足够覆盖「往上翻一会儿」，
  又不至于让首屏挂太多。
- **每次追加 60 条**（`WINDOW_STEP`）。
- **距顶部 80px 内触发追加**（`NEAR_TOP_PX`）。
- 窗口**只增不减**：用户往上翻过之后，不因为新消息到达就把已展开的历史收回去
  （收回去会让正在读的位置跳走）。

### 2.3 滚动位置必须保住

向上追加时，内容会**在上方**长出来；若不补偿，用户看到的内容会整体下移一屏。
做法：
1. 追加前记录 `scrollHeight`；
2. `useLayoutEffect` 里（追加渲染完成后）把 `scrollTop` 加上 `新 scrollHeight - 旧 scrollHeight`。

★ 为什么用 `useLayoutEffect`：要在浏览器绘制前补偿，否则会看到一帧跳动。

### 2.4 搜索跳转要能跳到窗口外

会话内搜索命中一条**比窗口更早**的消息时，`getElementById` 拿不到节点（没渲染）。
处理：跳转前算它在 `visibleMessages` 里的下标，若不在当前窗口内，
**把窗口扩大到刚好包含它**（再留几条上下文），渲染完成后再滚过去。

### 2.5 顶部给一个显式入口

窗口之外还有消息时，列表顶部显示一行按钮
「加载更早的消息（还有 N 条）」。滚到顶部会自动加载，但**按钮仍然要有**——
触控板/滚轮行为在部分设备上不可靠，显式入口是兜底，也让用户知道「上面还有」。

### 2.6 不做的事

- **不做**双向虚拟化 / 滚动条高度模拟；
- **不改**数据加载策略（仍是全量拉取）；
- **不改**消息行的 DOM 结构与 `id`（搜索、多选、引用全依赖它们）；
- **不改**自动滚到底的行为（新消息到达仍滚到底，这是既有语义）。

## 3. 兼容与迁移

| 项 | 兼容性 |
|---|---|
| 渲染窗口 | 纯渲染层，无数据/协议变更 |
| 搜索跳转 | 命中在窗口内 → 行为不变；在窗口外 → 自动扩窗后跳转 |
| 多选「全选」 | 仍按**已加载的全部**消息选（数据层语义不变），不是只选渲染出来的那些 |
| 会话切换 | 窗口计数重置为初始值（回到该会话时从最近 60 条开始） |

## 4. 测试计划

| 文件 | 覆盖 |
|---|---|
| `lib/messageWindow.ts`（新建） | `windowStart` / `expandCount` / `shouldLoadMore` / `countToInclude` 的边界（0 条、少于窗口、恰好等于、超出） |
| `lib/messageWindow.test.ts`（新建） | 上述纯函数的单元用例 |
| `components/ChatPage.test.tsx` | **200 条消息的会话只渲染初始窗口条数**（断言 DOM 节点数，确定性强于计时）；点「加载更早的消息」→ 渲染条数增加且最新消息仍在；滚到顶部（`scrollTop=0` 触发 scroll）→ 自动扩窗；搜索一条窗口外的老消息 → 扩窗并出现该节点；切会话 → 窗口重置 |

★ **关于「首屏耗时前后对照」**：vitest 里的计时断言在 CI/不同机器上极不稳定，
不作为主判据。主判据是**渲染出的消息节点数**（确定性）；另加一条**粗粒度**耗时上限
（如 < 5s）只用于捕捉灾难性回归，注释里写明它不是性能基准。

## 5. 不做 / 边界

- **不做**真正的虚拟列表（高度不定 + 要改每行容器，风险不抵收益）。
- **不做**服务端分页（接口与 E2E 解密链路都要动）。
- **不做**「窗口外消息的 DOM 占位」——窗口外的消息就是没渲染，搜索/锚点按需扩窗。
- 本轮**与 d.31 的 `msgCache` 上限合流复测**：确认渲染窗口化之后，存储侧仍受 20 会话 LRU 约束
  （两者解决的是不同层面，不能互相替代）。
