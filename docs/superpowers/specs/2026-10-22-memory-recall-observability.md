# 记忆召回的可观测性（d.27.1.7.0）

日期：2026-10-22
状态：已实现
相关：`docs/superpowers/specs/2026-10-21-memory-recall-ranking.md`（打分与多样性重排那一轮）、`docs/HANDOFF.md` §5 #4

## 1. 问题

记忆三层跑起来以后，用户看不到「它到底记了什么、这次带上了什么」。已有的记忆页只给两样东西：条目清单，以及一个召回预览（列出召回到的条目 + 注入文本）。这有三个缺口：

1. **召回被当成注入**。预览列了 5 条语义记忆，注入文本里只有 3 条半——第 4 条被 1200 字符预算截断，第 5 条整条没进。用户看预览会以为「5 条全带上了」，于是「我明明记着，它怎么没用」和「我记着的东西它怎么没用」这两种反馈混在一起，谁也分不清是排序问题还是额度问题。
2. **同键旧值被误判成漏召回**。语义层有一条时效覆盖：同一个主题键只保留最新值，旧值不参与注入。这条规则在界面上完全隐形——用户看到「称呼」只出来一个新值，会怀疑旧值丢了，实际是它被正常覆盖了。
3. **没有历史**。预览只算「这一句话会召回什么」，而用户想知道的是「刚才那一轮到底带上了什么、回答里用到了没有」。聊完了想知道，就再也问不出来了。

其中第 3 点最容易被带偏成「再问一次模型你用了哪条记忆」——那是第二次 LLM 成本，而且答案不可复现（同一份注入这次说用了、下次说没用），用户在记忆区看到的「引用」就成了玄学。

## 2. 决策

### 2.1 「召回 ≠ 注入」是一条硬口径，必须在格式化层算

只有 `format.ts:186` 的 `summarizeInjection` 同时知道两件事：**参与分层的候选**（`trace.candidates`）和**真正进了文本的行**（`trace.injected`）。差集必须在这里算，理由和 `agentStream.ts` 的来源脚注同口径——**编排层拼，与模型是否自述无关**。把差集留给调用方算，等于把「召回 ≠ 注入」这个口径散落到每个 UI 里各写一遍，写一遍偏一次。

于是注入旁路有了唯一的数据结构 `MemoryObservability`（`format.ts:158`）：

| 字段 | 含义 | 为什么必须有 |
| --- | --- | --- |
| `injected` | 实际进入文本的每一行，带来源 `id`、`layer`、**截断后的** `content`、`truncated` | 「带上了什么」的唯一真相 |
| `dropped` | 召回了却没注入的条目 + 原因（`budget` / `superseded`）+ 原文 | 让「没带上」能被解释，而不是被猜 |
| `scores` | 条目 id → 召回打分（语义 + 情景合并） | 排序口径原本算完即丢，用户看不到「凭什么这几条」 |
| `superseded` | 被同键新值覆盖掉的旧条目（key / loserId / winnerId） | 单独一档原因，避免显示成漏召回 |
| `counts` | 三层召回条数（注入前） | 与 `injected.length` 不相等正是这一轮要暴露的东西 |

两个细节：
- **`truncated` 必须与 `budget` 分开**。截断的那条是「注入了一半」，不是「没注入」；混为一谈会让计数对不上。
- **`dropped` 带原文**。只给 id 的未注入项，用户照样看不懂「哪条被裁了」。

类型归属这么定是为了消掉模块环：结构定义在 memory/format.ts（差集只有格式化层算得准），`agentRuntime/context.ts` 只转发（`BuiltContext.recallTrace`，`context.ts:60`），不反向依赖 agent 运行时。

召回侧配合改了两处：`recallMemory` 多带 `scores` / `superseded`（`recall.ts:259`），`supersedeSemantic` 除了活集还返回被覆盖清单。打分只用于展示与相对排序，**保留 4 位小数**——否则 UI 会出现 `0.3247109382471093` 这种长串。开关关闭或读取抛错时五个字段全空，注入侧照旧零注入，`systemPrompt` 严格等于 `basePrompt` 这条不变式没动。

### 2.2 「用到了没有」= 字符串级词重合，判据保守且可调

`attribution.ts:41` 的 `matchUsage` 只做一件事：**实际注入文本**（截断后的 `content`，不是原始条目）的词有没有出现在回答里，出现多少个**不同词**。

- `USAGE_MIN_HITS = 2`：单个大词双词都太容易白撞。
- 只有 1 个命中词时，词本身长度 ≥ `USAGE_STRONG_TOKEN_LEN = 3`（`react`、`8787` 这类）也算——长词几乎不会白撞。
- **跳过工作层与 `focus` 聚合行**：工作层就是刚才那几轮对话，回答必然复述其中的词，「命中」恒为真，等于没有信息量，还会把真正的长期记忆信号淹掉。
- 比对对象是截断后的 `content`：模型看到的只有被预算裁过的那半句，拿全文比对会把「模型没看到的部分」也算成命中。

判据刻意保守——**宁可漏报「其实用了」，也不要误报「用了这条」**，误报会让用户以为记忆系统在瞎认功，比沉默更伤信任。因此界面上必须写「疑似引用」，不能写「已使用」：这是提示层与回答层的重合度指标，不是因果证明。两个阈值都是导出常量，想调紧调松改一处即可。

### 2.3 留档单独一个 localStorage 键，且不参与导出

`heming.memory.recallLog.v1`（`recallLog.ts:19`）。为什么不复用已有的持久化：

- `heming.selfAudit.v1` 是自我修改的**回滚时间线**，混进召回日志会让回滚列表出现无关条目；
- 任务区 `TaskRecord` 只给「从任务区发起的流」建档，日常聊天不建档，而日志要覆盖日常聊天；
- 三层记忆键是**用户数据**（可导出/导入），日志是**本机诊断数据**，导出时不该带走。

护栏压得很小：环形 40 档（`RECALL_LOG_MAX`）、字节 256KB（远小于单键通用护栏 1.2MB）、注入内容留 120 字、提问留 200 字。裁剪按新→旧累加，**首档无条件保留**——否则一条超长档案会让日志永远写不进任何东西。`record()` 入参不符合契约或落盘失败一律返回 `null`，调用方静默降级。

### 2.4 接线：两个钩子都拿不到 streamId，用 `agentId::userText` 中转

旁路只在「拼装提示词」时存在，日志只能在「轮次收尾」时写，而这两个钩子（`ChatPage.tsx:1345` / `:1476`）**都没有 streamId**：前者在流启动前，后者只带 `agentId/userText/assistantText/status`。

`RecallRecorder`（`runRecorder.ts:31`）就是这座桥：`capture()` 挂旁路，`settle()` 取旁路 → 判引用 → 落日志。键取 `agentId::userText`——同一轮里二者必然相同；重试会覆盖旧档（重试本来就该按新的注入算），并且**消费即删**，同一份旁路不会记两档。零注入（本轮没带记忆）不留档也不记日志，日志里因此不会出现「注入了 0 条」的噪音档。待收尾档上限 24、孤儿 10 分钟过期，全程 try/catch：**任何一步异常都只是这一档没记上，绝不影响发送与流式渲染。**

### 2.5 记忆区展示：预览讲「这次」，记录讲「刚才」

- 预览结论行改成 **`召回 N 条 → 注入 M 条 · 预算占用 X / 1200 字符`**，两个数字不相等正是设计要暴露的。
- 每层逐条带 `· 打分 0.xxx` 与状态：`· 注入` / `· 注入（超预算已截断）` / `· 预算外，未注入` / `· 被同键新值覆盖`。覆盖条数另起一句提示「这不是漏召回」。
- 新增「召回记录」区：默认列最近 3 档（最近优先），可展开全部；每档默认只给结论，点「明细」看逐条注入（层名 + 打分 + 截断 + `▪ 引用`）与未注入（`✕ 原因：原文`）。清除走 `ConfirmDialog` 二次确认。
- 语义卡的 meta 行追加注脚 `· 最近注入 2026-10-17 · 疑似引用 2026-10-17`，由 `buildTouchIndex`（`recallLog.ts:213`）一次遍历建索引——按条目逐个扫日志会是 O(卡数 × 日志数)。

## 3. 隐私边界

召回日志与注入旁路**全部只落本机 localStorage**，不进消息、不进 SQLite、不上云，也不参与记忆导出（`.json` 里只有三层 + 设置）。日志内容上限截断到 120/200 字，是为了「够解释」而不是「留全文」。总开关关闭时既不记录也不召回，日志区自然不再新增。

## 5. 已知边界与后续

- **「疑似引用」不覆盖工具调用与检索链路**：只看最终回答文本，中途引用了记忆但正文没复述的，记为未引用。
- **旁路按 `agentId::userText` 配对**：同一智能体在两个会话里发完全相同的一句话、且两轮流同时在飞，会串档。真实聊天里几乎不可能（人不会同一秒打两遍同一句），但多端并发要严格化就得等钩子带上 streamId。
- 日志只记「带记忆的生成」，纯闲聊不记——这是有意的：40 档环形额度要给诊断，不该被闲聊挤满。
- 打分目前只展示数值，没展示「为什么是这个分」（重合度 / 衰减 / 置信度三项拆分）。要做的话得把 `rankSemantic` 的中间量也带出来，属于下一轮。
