# d.43 · 系统能力包：插件声明技能与远程 MCP 服务

- 日期：2026-11-01
- 相关版本：d.42.1.11.0（基线）、本 spec = d.43.1.11.0（特性位 +1）
- 涉及包：`packages/web`（纯前端，不改服务端、不改共享协议）
- 上游判断：d.42 把插件做成了**系统级生命周期**（安装/启停/卸载按包管理），但包内容只有技能，和「智能体技能」的区别只体现在存储与归属上。本轮把插件升级为**系统能力包**：一次装入可带入技能，也可带入远程 MCP 服务，让「系统级功能」有真实承载物。

## 0. 问题

- **插件没有工具能力**：d.42 的插件只能加提示词。用户说「插件是系统级功能」时，期待的是装一次、整个工作区多一类可调用能力，而不是给某个智能体加几段技能。
- **MCP 是现成的工具接缝**：HTTP/stdio 客户端、工具发现、工具级开关、HITL 风险判定都已存在；插件只需要声明远程服务，不应另造一套工具运行时。
- **来源不可辨认**：MCP 服务目前只有 `preset / manual / registry` 三种来源；从插件装进来的服务会被当成「手填」，用户无法判断它属于哪个包、该不该随包卸载。

## 1. 决策

### A. 清单 v2：技能与远程 MCP 服务并列

```json
{
  "schemaVersion": 2,
  "id": "acme.weather",
  "name": "天气能力包",
  "version": "1.0.0",
  "description": "天气查询技能与远程 MCP 服务",
  "author": "Acme",
  "skills": [
    { "name": "出行建议", "instructions": "结合天气给出出行建议。" }
  ],
  "mcpServers": [
    {
      "key": "weather",
      "name": "天气服务",
      "url": "https://mcp.example.com/weather",
      "description": "查询当前天气与预报"
    }
  ]
}
```

| 字段 | 规则 |
|---|---|
| `schemaVersion` | 接受 `1`（技能包）与 `2`（能力包）；v1 出现 `mcpServers` 一律报错，提示升级到 2 |
| `skills` | 0–50 个（v2 允许纯 MCP 包；v1 仍要求至少 1 个） |
| `mcpServers` | 0–10 个；`key` 匹配 `^[a-z0-9][a-z0-9-]{0,31}$` 且插件内唯一；`name` ≤64；`description` ≤200；`url` ≤2048 |
| 能力总数 | `skills.length + mcpServers.length >= 1`，否则「插件至少要包含 1 项能力」 |
| `url` | 只接受 `https:`；`http:` 仅限 `localhost` / `127.0.0.1` / `[::1]`；禁止 URL 内嵌用户名密码 |
| 未知字段 | 静默丢弃，不建档、不进存储 |

**为什么只有 HTTP、没有 stdio/命令**：stdio 会在用户机器上拉起子进程，等于安装即执行第三方代码；这与 d.42「插件不执行随包代码」的口径冲突。本地进程类集成仍走接口区手动配置或 Registry 安装，保持一次显式确认。**为什么清单里没有请求头/令牌**：插件包会被转发、存档，不能把凭据写进包；需要鉴权的服务在接口区补请求头（d.36 起该字段走 `safeStorage` 加密），插件更新会保留用户请求头。

### B. 安装语义：技能物化 + MCP 服务注册

- **技能**：沿用 d.42——`source: "imported"`、`pluginId`、按名称增/改/删、默认分配与显式分配追加。
- **MCP 服务**：每个声明物化为一条普通服务配置：
  - 稳定 id `plugin:<pluginId>:<key>`（`key` 不含冒号，工具键 `serverId::toolName` 的 `::` 分隔不受影响）；
  - `origin: "plugin"`，`enabled` 跟随插件启用状态；
  - **不设置请求头**；更新时保留用户在接口区补的 `headers` 与已启用工具集合。
- **冲突**：若同 id 已存在且 `origin !== "plugin"`，安装整体失败并说明冲突 id，不覆盖用户手填服务；冲突检查在写入技能之前完成。
- **更新**：同 id 再装 = 更新；新增/刷新声明的服务，清单里移除的服务删除（只删 `origin === "plugin"` 且 id 在旧 `serverIds` 内）。
- **停用**：插件与全部技能置为未启用，其 MCP 服务也 `enabled=false`（工具随之不可用，但配置与工具清单保留）。
- **卸载**：删技能（含绑定/统计）与服务（含工具清单与工具启用键），再删插件记录。手填服务、同名技能不受影响。

### C. 存储与迁移

- 插件记录新增 `serverIds: string[]`；旧记录缺省视为 `[]`（d.42 数据无需迁移）。
- `heming.plugins.v1` 结构与容错不变：逐条校验，坏条目丢弃，整体损坏回退空表。
- 服务配置仍写 `heming.mcp.servers.v1`（d.36 加密信封），工具清单/启用状态沿用现有键。

### D. 展示与入口

- **安装预览**：除技能外列出 MCP 服务名与主机；单独一行「网络访问：host1、host2」，并写明「工具需在接口区连接并启用，调用仍走人工确认」。
- **插件卡**：显示技能数、服务数、服务名标签；有服务时提供「查看接口」入口（跳接口区）。
- **接口区**：`origin: "plugin"` 的服务显示「插件」徽标；说明其随插件启停、卸载。
- **文案**：插件页页脚改为「只声明技能与远程 MCP 服务；不执行随包代码、不携带密钥、安装时不联网」。

### E. 安全边界

| 风险 | 处置 |
|---|---|
| 安装即产生网络外发 | 安装前展示主机清单；安装本身不连接，连接由用户在接口区发起 |
| 远程服务返回恶意工具声明 | 沿用 MCP 口径：`annotations` 不可信，风险按工具名启发判定，未知按 `write` 问人 |
| 工具自动启用 | 不自动连接、不自动启用工具；与 Registry 一致，发现后由用户逐个打开 |
| 凭据进包 | 清单禁止请求头/凭据；鉴权在接口区补，走安全存储 |
| 安装包可携带本地执行 | 只允许 HTTP；stdio/命令字段不在 schema 内，未知字段被丢弃 |
| 与手填服务 id 冲突 | 安装前检查并整体失败，不覆盖用户配置 |

## 2. 明确不做

- **不从插件启动本地进程**：stdio / `command` / `args` 不在清单内；本地集成走手动或 Registry。
- **不在清单里携带密钥、请求头或环境变量**：不做安装时凭据收集。
- **不自动连接、不自动启用工具**：插件只负责「登记服务」，连接与授权仍由用户操作。
- **不做 OAuth 发现 / 动态注册 / 在线市场 / 签名校验**。
- **不做插件级智能体分配**：技能仍按智能体分配；MCP 工具维持系统级可用（模型能力闸与 HITL 不变）。
- **不把插件服务的工具标成 `origin: "plugin"`**：工具由 MCP 提供者统一构建，插件归属落在服务配置上，避免为同一批工具注册第二个提供者导致重名竞争。

## 3. 验收

1. v2 纯技能包、纯 MCP 包、混合包均可安装；v1 包行为与 d.42 完全一致。
2. 安装混合包后：技能出现在技能区「已装」，服务出现在接口区且带「插件」徽标。
3. 接口区连接服务后能看到工具；工具默认未启用，启用后聊天编排可调用（走既有 HITL）。
4. 停用插件：技能不参与路由，服务不再连接/不可用；重新启用恢复。
5. 更新：技能按名称增/改/删；服务按 `key` 增/改/删；用户在接口区补的请求头与已启用工具保留。
6. 卸载：技能、服务、工具清单、工具启用键、分配一并清理，手填服务与同名技能不受影响。
7. 非法清单（v1 带服务、远程 http、URL 带账号密码、key 重复、两类能力都为空）给出中文错误且不落盘。
8. 全量门禁 `pnpm -r build && pnpm -r --workspace-concurrency=1 test` 全绿。
