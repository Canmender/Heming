## 0. 结论先行

1. **推荐方案 A'（就地信封 + 逐条密文 + 内存视图 + 批量 IPC）**，不搬 IndexedDB、不搬主进程文件（理由见 §3）。
2. 两个键分别处理：
   - `heming.msgCache.<convId>`：新容器格式 `{"__hemingMsgCache":"v2","items":[...]}`，**逐条密文**、`id` 留明文做索引，读侧按 id 定点解密（O(1)），新增批量通道兜底。
   - `heming.e2e.chains.<convId>`：**整值信封 v1**（复用 d.36 形状 `{"__hemingEnc":"v1","data":...}`），写入前做「加密后立刻解密自校验」，另留一个版本的明文备份键。
3. 三阶段发布：P1 消息缓存 → P2 棘轮状态 → P3 清理残留明文。每阶段独立版本、独立门禁、可单独回滚。
4. 唯一实质性缺陷是**配额**（缓存本来就接近 5MB 上限，加密后增长约 50%），处置办法与降级阶梯写在 §5.3。
5. 三个需要拍板的问题在 §9（默认值已给推荐）。

**明确不改善的场景**（先写在最前面，避免把安全承诺说大）：同源脚本、DevTools、进程内存与崩溃转储、同用户的恶意进程只被「提高门槛」，不被阻止。详见 §1.3。

## 1. 现状与威胁模型

### 1.1 现状：到底有多少明文、在什么频率上被读写

d.36 只加密了三把钥匙，代码里对此有明确注释：`packages/web/src/lib/e2eSession.ts:198`（「身份键走 secure 层；chains/deferred/msgCache 仍在下面的普通 readJson 路径」）。四个键的实际形态：

| 键 | 内容 | 体量（估算） | 读写频率 | 今天是否加密 | 证据 |
|---|---|---|---|---|---|
| `heming.msgCache.<convId>` | **解密后的消息正文** `CachedMsg[]`（含 `plain.text`） | 每会话 ≤500 条（`CACHE_CAP`），最多 20 个会话；单条约 200-1000B | 每落定一条消息：读 2 次（命中判断）+ 整数组重写 1 次 | 否 | `e2eSession.ts:44`、`:999`、`:109-115`、`:955-965` |
| `heming.e2e.chains.<convId>` | 棘轮状态：发送链 `ck/n`、接收链 `ck/n`、`msgKeys` 乱序窗口（≤1000 条）、`opened` 去重表 | 每会话约 60-100KB（窗口满时） | 每落定一条消息：读 1 次、整文件重写 1 次 | 否 | `e2eSession.ts:42`、`:156-169`、`:672`、`:740`、`:718-741` |
| `heming.e2e.deferred.<convId>` | 缺链/超窗暂挂的**对端密文信封**（不是明文） | ≤50 条 | 低（仅 defer 时） | 否（内容本身已是 E2E 密文） | `e2eSession.ts:11`、`:43`、`:252-259` |
| `heming.msgCache.lru.v1` | 会话账本：`convId → 最后使用时间` | 20 条 | 热路径只改内存，60s 节流落盘 | 否（仅元数据） | `e2eSession.ts:1002`、`:1009`、`:1082-1086` |

三点必须写清楚的现状事实：

- **热路径的频次单位是「消息」，不是「token」**：`appendCache` 明确跳过 `chaindist` 与 `chunk`（`e2eSession.ts:800`），流式增量不进缓存。所以「每条消息过一次 IPC」与「每片 token 过一次 IPC」是两个数量级的问题，前者可做，后者不可做。
- **读写全程同步**：`readJson/writeJson` 就是 `localStorage.getItem/setItem`（`e2eSession.ts:184-196`）。这是本轮最关键的技术约束——`secret-store.js` 的桥是同步 `sendSync`（`packages/desktop/secret-store.js:60-72`），而 d.36 的注释已经写明这条前提：「谁把这层用到高频路径，谁就得先改成批量/异步」（`packages/web/src/lib/secureStorage.ts:9-10`，`packages/desktop/preload.js:137-138`，`packages/web/src/types/heming.d.ts:69-71`）。
- **缓存被当作「按 id 查明文」的索引使用**：`ChatPage` 的解密 handler 只做 `msgCache.list(conv).find((c) => c.id === env.id)`（`components/ChatPage.tsx:643`、`:680`），并没有遍历渲染。这一点决定了「不必一次解密全部 500 条」，是 §2.1 能成立的关键。

### 1.2 威胁模型：谁站在哪里，能看到什么

|---|---|---|---|---|---|

| T2 | 同机其他用户或低权限进程 | 同上（文件权限 + 明文 JSON 直接可读） | 改善：读不到用户 profile，或读到了也解不开 | 是 | 同上 |

| T8 | 服务端 / 网络 | 只有密文（E2E） | 不变 | 不适用 | 红线未动 |

### 1.3 明确是伪需求（做了也不会改善）的几项

- **「让 DevTools 里看不到消息正文」**：会话渲染必须把明文放进 DOM，磁盘加密不改运行时形态。零收益。
- **「防止同源脚本读缓存」**：只要解密能力留在渲染层，任何同源脚本都能通过 `__heming_secrets.decrypt` 解任何它拿到的密文（`preload.js:148-166`）。真要做就得把解密与渲染搬进主进程（等体重写），且脚本仍能读 DOM。本轮不做，也不承诺。
- **「加密顺带省空间」**：base64 反而膨胀约 37%，逐条信封还会再加每条几十字节（§5.1）。
- **「隐藏会话 ID、活跃时间」**：`heming.msgCache.lru.v1` 只有 `convId` 与时间戳，是服务端可见的元数据，加密收益极低；本轮不做（§8 第 3 条）。
- **「防内核级/管理员攻击者」「防用户自己导出」**：前者在威胁模型外；后者是用户主动行为，导出函数本身不读存储、不联网（`packages/web/src/lib/export/conversation.ts:4-7`）。

### 1.4 两条不可回避的约束（所有方案都受它约束）

**B1：`msgCache` 事实上近乎不可再生，迁移必须非破坏性。**
收到的消息只能靠链窗口内的 `msgKeys` 再解（`e2eSession.ts:696-703`，落后超 `WINDOW`=1000 即永久 `defer`），**自己发出的消息本机没有接收链**（发送链 `ck` 已推进，旧 `msgKey` 不可再派生），一旦缓存丢失就永久显示「无法解密」。
顺带发现一处**现有文案不准确**：`StorageUsageCard.tsx:199-201` 说清理缓存后「重新拉取并解密即可恢复」，这对超出窗口的旧消息并不成立（依据即 `e2eSession.ts:699-703`）。P1 应顺手改成「仅窗口内的近期消息可恢复」，否则用户会以为清缓存是零代价操作。

**B2：`chains` 是解密能力的唯一来源，写坏即历史消息永久锁死。**
d.36 规格已把这一点写进不做的理由（`2026-10-23-d36-safestorage.md:33-34`）。因此任何写入都必须满足「**先确认新值能被自己解开，再覆盖旧值**」，且不能有「先删后写」的窗口。

## 2. 可选方案对比

四个方案的共同前提：不新增任何对外网络能力；浏览器端（无桥）行为不变；不解密到「第二个存储位置」（不产生明文副本）。

### 2.1 方案 A：safeStorage 就地信封 + 内存视图 + 批量 IPC

**形态**

- `chains`：沿用 d.36 的整值信封，零新格式
  ```json
  { "__hemingEnc": "v1", "data": "<base64(safeStorage.encryptString(JSON))>" }
  ```
  读侧直接复用 `secureGetItem/secureSetItem`（`secureStorage.ts:115-166`、`:194-224`），即 d.36 已经跑过测试的懒迁移路径。
- `msgCache`：容器 + **逐条密文 + 明文 id 索引**
  ```json
  { "__hemingMsgCache": "v2",
    "items": [ { "id": "m-1", "d": "<base64 密文>" },
               { "id": "m-2", "m": { ...旧明文条目（迁移期兼容）... } } ] }
  ```
  逐条而不是整数组一封，是因为 `append` 每条消息都会整数组重写（`e2eSession.ts:955-965`）：整数组一封会把每次 append 变成「重加密全量 200-600KB」，逐条则只加密新增那一条，O(1)。`id` 留明文，使读侧能按 id 定点解密（`ChatPage.tsx:643` 只需要一条），避免冷读一次性 DPAPI 解 500 条。
- 内存视图：沿用现有 `cacheView` 的「raw 变化才重解析」模式（`e2eSession.ts:936-952`），并新增 `chainsView`（同样模式）把 `loadChains` 的每消息一次 DPAPI 解密降到 0。
- 桥：新增两条**批量**同步通道 `secret:encryptMany` / `secret:decryptMany`（一次 IPC 传数组，主进程循环），供迁移与批量场景使用；热路径仍是一次单条调用。

**改动面（文件级）**

| 文件 | 改动 |
|---|---|
| `packages/web/src/lib/e2eSession.ts` | `msgCache` 三个方法改走容器编解码；新增 `get(convId,msgId)`；新增 `chainsView`；`loadChains/saveChains` 改秘密路径；新增迁移入口 |
| `packages/web/src/lib/cacheEnvelope.ts`（新建） | 纯函数：容器三态解析、条目编解码、旧明文条目识别（可单测，无 DOM 依赖） |
| `packages/web/src/lib/secureStorage.ts` | 新增 `secureSetItemVerified`（加密→解密→比对→写入）；导出容器常量；批量桥封装（一次 IPC） |
| `packages/web/src/components/ChatPage.tsx` | `:643`、`:680` 两处 `list().find()` 换成 `get()` |
| `packages/desktop/secret-store.js` | 新增 `encryptMany/decryptMany` 与两条 IPC 通道（仍无网络，红线测试保持） |
| `packages/desktop/preload.js` | `__heming_secrets` 增两个方法（`:148-166`） |
| `packages/web/src/types/heming.d.ts` | 桥类型补两个方法（`:72-76`） |
| `packages/web/src/lib/storageUsage.ts` | `:57` 组名「明文缓存」→「消息缓存」（加密后名不副实） |
| `packages/web/src/components/StorageUsageCard.tsx` | `:196-201` 清理目标名与说明文案；`:492` 不可再生说明补充「消息缓存内的自发消息不可再生」 |
| `packages/web/src/components/KeyStorageCard.tsx` | `:83` 的「尚未加密（后续单独处理）」按阶段改写 |

**热路径开销**

| 动作 | 今天 | 方案 A' |
|---|---|---|
| 收到一条消息 | 读 `chains`（parse ~80KB）+ 写 `chains`（序列化 ~80KB）+ 读缓存数组 + 写缓存数组 | 读 `chains` 命中内存视图（0 解密）+ 写 `chains`（1 次加密 ~80KB + 自校验 1 次解密）+ 缓存 1 条加密 + 整数组 1 次 setItem |
| 发出一个 chunk | 不落缓存（`:800`） | 不变 |
| 打开旧会话 | 0 次解密 | 0 次解密（按 id 定点解） |

**原子性 / 崩溃安全**：单键 `setItem` 本身原子；`chains` 增加「加密后立即解密比对，一致才写」，不存在「写进去但解不开」的窗口。崩溃最多丢「最后一条尚未落盘的缓存条目」，且 `chains` 不会出现半写状态。

**迁移成本**：中。`chains` 几乎是改两个函数名；`msgCache` 需要新容器编解码 + 一次读侧兼容（三态） + 迁移批次调度。

**回滚路径**：读侧同时认三种形态（旧明文数组 / v2 容器 / v1 信封），所以**代码级回滚**只需发布「读三态、只写明文」的版本；数据不需要反向迁移。降级到更老的版本（不认识 v2）会导致缓存视图丢失，见 §4.5。

**浏览器端（无桥）降级**：保持今天的明文数组形态，行为零变化（与 `secureStorage.ts:12-13` 的既定态度一致：宁可如实说明，也不假装加密）。

### 2.2 方案 B：搬出 localStorage（主进程文件 + `app://` 路由）

**形态**：主进程新增 `secret-fs.js`，把 `chains` 与 `msgCache` 以文件存放（`userData/` 下按会话一文件，内容 safeStorage 加密）；渲染层经 `fetch("app://...")` 或异步 IPC 读写。`app://` 已注册为 `privileged + secure`（`packages/desktop/main.js:66-71`，`:42-45`），`supportFetchAPI: true`，技术上可承载。

| 维度 | 评估 |
|---|---|
| 改动面 | 新增 `secret-fs.js` + `main.js` 注册 + `preload.js` 桥 + `e2eSession` 的 `loadChains/saveChains` 变 async（牵动 `handleChainDist` 的同步导出 `e2eSession.ts:820`、38KB 的 `e2eSession.test.ts`、`sweepDeferred`）+ `storageUsage` 失去可见性（要新增主进程报尺寸的通道） |
| 热路径开销 | 每条消息一次异步 IPC + 一次文件写（原子写是 tmp+fsync+rename，`packages/desktop/file-fs.js:17-18`、`:253-291`），比 localStorage 慢；且**发送路径要等落盘才能回包**（B2 要求），延迟直接压在收发上 |
| 原子性 / 崩溃安全 | 最好（rename 在 NTFS 上原子，且已有成熟先例） |
| 迁移成本 | 高（同步契约 → 异步契约贯穿整条 E2E 链路） |
| 回滚路径 | 难：两套持久化并存期必须双写双读，长期维护 |
| 浏览器降级 | 无桥时仍需保留 localStorage 明文路径 ⇒ 双实现永久共存 |
| 安全收益 | 对 T1/T2/T3 与方案 A **等价**（文件与 LevelDB 都在同一用户目录、都由 DPAPI 保护）；真正的收益只是**配额**与原子写 |
| 新攻击面 | `app://` 处理器目前只服务构建产物目录并有目录穿越防护（`main.js:139-164`、`app-protocol.js:55-68`）。要加数据路由就得另建 scheme 或另一套路径白名单，把「存储问题」变成「协议面问题」；同源脚本仍能 fetch（`corsEnabled: true`），安全上不多得一分 |

**结论**：收益（配额、原子写）可以用更小的代价在 A 里拿到；代价（异步化整条 E2E 链）远大于收益。**不推荐本轮做**。

### 2.3 方案 C：IndexedDB + WebCrypto（密钥仍由 safeStorage 保护）

**形态**：主进程生成/保管一个 32 字节数据密钥，经一次 IPC 交给渲染层；之后消息缓存与链状态写进 IndexedDB，用 WebCrypto AES-GCM 加解密（原语已在 `lib/e2eCrypto.ts:182-211`，密钥派生也现成 `:170-179`）。

| 维度 | 评估 |
|---|---|
| 改动面 | 新密钥生命周期模块；`msgCache` 接口全异步（`e2eSession.ts:117-124`，`e2eSession.test.ts` 里有 **17 处** `msgCache.list` 同步断言）；`chains` 异步（`handleChainDist` 同步导出 `:820`）；`storageUsage` 口径失效（IDB 不进 localStorage 统计，得改用 `navigator.storage.estimate` 或自记账）；`StorageUsageCard` 水位条与清理入口全部要重写 |
| 热路径开销 | **最优**：无 IPC、AES-GCM 吞吐远高于 DPAPI；但 IDB 是异步事务，`append` 失去「同步落盘」语义 |
| 原子性 / 崩溃安全 | 单事务原子；但「链状态」与「缓存」跨 store 一致性要自己保证 |
| 迁移成本 | 最高（同步→异步贯穿 + 存储计量重写 + 双存储迁移） |
| 回滚路径 | 最难（两存储并存期，谁是真源要拍板） |
| 浏览器降级 | 无桥时数据密钥无处安放：要么明文 IDB（假装加密），要么退回 localStorage ⇒ 双代码路径 |
| 安全收益 | **与 A 等价**：密钥封装后仍存 localStorage，同用户攻击者能解封；换账户/换机同样解不开。也就是说它不比 A 更安全，只是更快、更大 |

**结论**：安全收益为零、工程代价最高。作为「配额真的不够用」时的后续优化项（P4 候选），不进本轮。

### 2.4 方案 D：混合（链走主进程文件、缓存走内存 + 落盘加密）

动机是「链小、关键 → 放主进程更稳；缓存大、可丢 → 加密落 localStorage」。但两个前提都不成立：

- 链并不低频：每条消息读一次写一次（`e2eSession.ts:672`、`:740`；发送侧 `:494`、`:525`）。放主进程文件等于把 `fs` 延迟放到发送路径上，比本地 localStorage 慢。
- 缓存并不可丢：见 B1，自发消息永久不可再生。

另外它同时背上方案 B 的异步化代价与方案 A 的容器格式代价，还多了一条「两处真源」的一致性风险。**不推荐**。

### 2.5 取舍表

| 维度 | A' 就地信封 | B 主进程文件 | C IDB + WebCrypto | D 混合 |
|---|---|---|---|---|
| 改动文件数（估） | 10 | 8 + 新模块，但牵动 38KB 测试与同步契约 | 12 + 新模块，牵动 17 处同步断言 | 12 + 两套机制 |
| 热路径新增开销 | 每条：1 次加密（~80KB，链）+ 1 次小加密（缓存条目）；读侧 0 次 | 每条：异步 IPC + 文件写（含 fsync） | 每条：AES-GCM（微秒级）+ IDB 事务 | 同 B + A |
| 原子性 | 单键 setItem 原子；链加自校验 | 最好（rename 原子） | 事务原子 | 混合，两处真源 |
| 崩溃窗口 | 丢最后一条未落盘缓存 | 无（落盘后才回包） | 无 | 无 |
| 迁移成本 | 中 | 高 | 最高 | 高 |
| 回滚 | 代码级回滚即可（读三态） | 难（双实现） | 最难（双存储） | 难 |
| 浏览器降级 | 明文，行为不变 | 明文，双实现 | 密钥无保护（假装加密或退回明文） | 明文 |
| 配额 | 受 localStorage 5MB 限制（**最大缺陷**，§5.3） | 不受限 | 不受限（数百 MB 级） | 部分解除 |
| 可测性 | 好（纯函数编解码 + 现有 jsdom 无桥路径） | 中（需 Electron 环境或桩） | 中（IDB 需 fake-indexeddb 之类） | 差 |
| 安全收益（对 T1/T2/T3） | 高 | 等价 | 等价 | 等价 |

## 3. 推荐方案与理由

### 3.1 结论

**采用方案 A'**：两块数据都留在原键位、就地加密，靠「内存视图 + 逐条密文 + 定点解密」把热路径开销压到可接受，不搬存储层。

### 3.2 五条理由（都能落到代码）

1. **同步契约不动**。`msgCache.list` 与 `loadChains` 的调用点遍布热路径（`ChatPage.tsx:643`、`store/chat.ts:415-428`、`e2eSession.ts:672-743`），改成异步会牵动整条解密链与 38KB 测试；A' 保持同步，只把值从明文换成信封，**调用方零改动**（除了两处换 `get()`）。
2. **迁移逻辑已被 d.36 验证过一遍**。`secureGetItem` 的懒迁移、幂等、失败保留明文、解不开备份，都已在 `secureStorage.ts:115-224` 实现并有测试；`chains` 复用它，P2 的真实工作量只有「自校验 + 备份 + 内存视图」。
3. **逐条密文把 O(n) 变 O(1)**。整数组一封会让每条消息重加密 200-600KB；逐条加密只碰新增的那一条，且 `id` 明文索引让读侧可以只解一条，冷读不再有「一次解 500 条」的卡顿。
4. **浏览器端行为零变化**。无桥 ⇒ 明文（与今天完全一致），jsdom 里所有现有用例继续走同一路径——这也是 d.36 用来证明「浏览器不受影响」的同款论据（`2026-10-23-d36-safestorage.md:131`）。
5. **回滚是代码级的，不是数据级的**。读侧认三态，回退版本只需「读三态、写明文」，不需要反向迁移脚本。方案 B/C 的回滚都要处理双存储真源，风险高一个档。

### 3.3 明确不覆盖的边界

| 边界 | 为什么覆盖不了 | 承诺口径 |
|---|---|---|
| 进程内存里的明文 | 解密后必须进 JS 堆，`cacheView`/`plainById` 都持有明文；JS 无法可靠清零 | 不承诺；UI 文案不提「内存加密」 |
| 用户解锁后的会话期间 | DPAPI 是用户级密钥，登录状态下本进程可随时解密 | 不承诺 |
| 同源脚本 / DevTools（T4、T5） | 桥是通用解密入口，DOM 里本来就有明文 | 状态卡不写「已加密，脚本也读不到」 |
| 同用户的恶意进程（T3） | DPAPI 无二次认证 | 文案写「需要系统账户权限才能解开」，不写「无法读取」 |
| `heming.e2e.deferred.*` | 内容已是端到端密文，加密只增复杂度（§8 第 2 条） | 明说不加密 |
| `heming.msgCache.lru.v1` | 只有会话 ID 与时间戳（元数据） | 明说不加密 |
| 服务端与网络 | 不在本轮范围（红线未动） | 不变 |
| 崩溃转储 / 页面文件（T6） | 属操作系统层 | 明说 |

### 3.4 为什么不是 B / C（一句话版）

B 的安全收益与 A 等价，却要用「异步化整条 E2E 链 + 新增协议路由」去换配额；C 的安全收益同样为零（密钥仍封在 localStorage），代价是最高。**配额**是唯一真实理由，而它可以先用「预检 + 可见降级」撑住（§5.3），真撑不住再单独立项换存储层。

## 4. 数据格式与迁移

### 4.1 版本号与形状

| 键 | 新形态 | 版本标记 | 读侧判定顺序 |
|---|---|---|---|
| `heming.e2e.chains.<convId>` | 整值信封（单调、整体读写） | `{"__hemingEnc":"v1"}` | `__hemingEnc` → 明文 JSON |
| `heming.msgCache.<convId>` | 容器 + 逐条密文 | `{"__hemingMsgCache":"v2"}` | `__hemingMsgCache` → `__hemingEnc`（兼容：若将来整值包裹） → 明文数组 → 无法识别 |

- **不引入 v2 信封去替代 v1**：`ENVELOPE_VERSION = "v1"` 是主进程与渲染层共同约定（`secret-store.js:22`、`secret-store.test.js:84-86`），换版本没有收益。
- **`msgCache` 的条目**：`{"id":"<消息 id 明文>","d":"<base64(safeStorage.encryptString(JSON.stringify(CachedMsg)))>"}`。`id` 明文是刻意设计——它是服务端可见元数据，换来 O(1) 定位。
- **迁移期允许混合数组**：条目可以是 `{id,d}`，也可以是 `{id,m:{...旧明文 CachedMsg}}`。这是**有意的**：允许增量迁移，避免「一次性重写整会话」这种高风险动作。
- **不允许**同一键里同时存在「v1 整值信封包着数组」与「v2 容器」两种外壳；外壳只有一个，条目级才是混合的。
- **不允许**把密文当明文再包一层（与 `parseStored` 的既有断言一致：`secureStorage.ts:89-109`）。

### 4.2 旧明文懒迁移：时机与批大小

| 触发点 | 做什么 | 批大小 | 理由 |
|---|---|---|---|
| 写入（`append`） | 新条目**一律写密文**；整数组一次 `setItem` | 1 条 | 新数据不产生明文，从源头止住 |
| 打开会话读到明文条目 | 空闲回调里把该会话的明文条目转密文 | **每批 ≤50 条**，一次 `setItem`；本会话最多 1 批/次打开 | 50 条约 10-25KB，单次加密 <2ms；与 `sweepDeferred` 的 `SWEEP_BATCH=5`（`e2eSession.ts:45`）同思路，但这里纯 CPU、不涉链，可放大 |
| 整机清理（P3） | 空闲时扫剩余 `heming.msgCache.*` 键 | 每次启动 ≤3 个会话、总预算 ≤300ms；成功后写 `heming.msgCache.migrated.v2` 标记，后续不再全扫 | 避免每次启动都遍历 |
| `chains` | 首次读取时整值迁移（一次写） | 1 个键 | 体量 60-100KB，整体迁移才原子；不做增量（增量会破坏链的原子性） |

**不在启动时同步集中迁移**：理由与 d.36 相同（ES 模块求值顺序会让「迁移先于 store 初始化」变脆弱，`2026-10-23-d36-safestorage.md:71-72`），且这里还多了 500 条量级的 CPU 成本。

### 4.3 幂等性与中断

- **条目幂等**：已是 `{id,d}` 的条目直接跳过；重复迁移是空操作（不会二次加密——二次加密会把密文当明文，这是必须钉死的断言）。
- **键级幂等**：每批写回前重新 `getItem` 与批次开始时快照的 raw 比对；不一致（有并发写/被外部清空）就放弃本批，下一轮重来。
- **写失败（配额）**：内存视图保持新值、磁盘保持旧值；标记「未落盘 N 条」并在水位卡显示；下一次 `append` 用完整数组重试整份写入。
- **崩溃**：最多丢最后一条未落盘的缓存条目。对**自己发出的消息**不适用此容忍——它不可再生（B1），因此自发消息的落盘失败要立即提示，不允许静默延迟。
- **单批原子**：一批一次 `setItem`，只有成功才更新内存视图。不存在「一半密文一半明文且读不出来」的状态（读侧本来就能读混合）。

### 4.4 「第二条消息读不出来」的四个具体成因与对策

这是本轮最需要提前拆开的风险，逐条对应：

| 成因 | 今天的实际行为 | 对策 |
|---|---|---|
| 读侧只认明文 JSON | `readJson` 解析失败返回 `null`（`e2eSession.ts:184-192`），`loadChains` 于是返回空链 `{recv:{}}`，随后发送会新建发送链并整文件覆盖（`:436-440`）⇒ **旧接收链永久丢失** | 统一读取入口 `readCacheValue/readChains`，按标记三态解析；解析出「信封但解不开」时返回空值**并置 `unreadable` 标记**，绝不静默当作空 |
| 半迁移 + 读侧把密文当明文 | 现状不会出现（没有迁移），本轮会 | 条目级类型判别（`d` 字段 vs `m` 字段），与外壳版本解耦；单测直接喂混合数组 |
| 并发写互相覆盖（接收回显与 `sweepDeferred` 同时 append） | 现状靠「同步执行、无 await 交错」保证（`e2eSession.ts:893` 的注释同理：「load→改→save 同步成段，无 await 交错」） | 规定所有写路径收敛到单一 `writeCacheValue(convId, mutate)` 入口（load-modify-write 同在一个同步块内），迁移批次同样走它 |
| 加密成功但写盘失败 | 配额满时 `writeJson` 抛错（`e2eSession.ts:961` 未捕获），消息直接显示失败 | 捕获配额错误 → 内存保留 + 「未落盘」可见 + 触发一次 LRU 淘汰后重试一次（§5.3） |

补充一条**读侧状态机**（实现时照此写，避免"返回空数组"与"解密失败"混为一谈）：

```
raw 为空            → 空缓存
{__hemingMsgCache}  → 逐条：{id,d} 解密；解密失败 → 该条置 unreadable，其余照常
{__hemingEnc}       → 整值解密后按 JSON 处理（兼容）
JSON 数组           → 旧明文（触发懒迁移）
其它/解析失败       → 空缓存 + unreadable 标记（UI 显示「本机无法解密该会话缓存」）
```

UI 侧要求：**「解不开」与「还没有消息」不能共用文案**（`store/chat.ts:384-455` 已有加载三态，需新增一个缓存不可解态）。

### 4.5 降级与「旧版读到新格式」

| 场景 | 旧版（d.36 前后）会怎样 | 后果 | 处置 |
|---|---|---|---|
| 旧版读到 v2 容器 | `JSON.parse` 得到对象而非数组 ⇒ `viewCached` 走 catch 返回 `[]`（`e2eSession.ts:942-948`） | 显示「没有缓存」；下一次 `append` 用空数组写回，**整会话缓存被清空**（自发消息永久丢正文） | 发布说明写明「降级会丢失本机消息缓存视图」；提供代码级回滚版本（读三态、写明文） |
| 旧版读到 `chains` 信封 | `readJson` 解析失败 ⇒ 空链 ⇒ 新建发送链并覆盖 | **历史消息永久解不开**，窗口内消息也解不开（灾难级） | P2 必须落一个明文备份键 `<key>.__pre_enc_plain`（d.36 同款思路，`secureStorage.ts:175-192`），并在发布说明写「回退需人工把备份键改名回原键」；状态卡显示「存在迁移备份」 |
| 新版读到旧明文 | 正常读取并懒迁移 | 无 | — |

### 4.6 配额与迁移峰值

- 增长来源：base64 约 ×1.37，逐条条目再加 `{"id":"…","d":""}` 约 60 字节。
- 峰值（迁移期间）：`msgCache` **无第二份副本**（就地覆盖，靠内存回滚），峰值 ≈ 终值；`chains` 因备份键存在一份明文副本，峰值 ≈ 2.37×，但绝对量只有 60-100KB/会话，可接受。
- 预检：迁移前用现成能力实测（`storageUsage.measureStorageUsage` 的已用量 `storageUsage.ts:201-249`，配额探针 `:269-320`）；剩余空间 < 预计增量 × 1.5 时**跳过迁移**，保持明文并在状态卡如实标注，不冒险。
- 迁移期明文备份的存续时间见 §9 Q3。

### 4.7 与现有 LRU / 统计的兼容点（容易踩）

- `listMsgCacheKeys` 只排除账本键（`e2eSession.ts:1012-1023`），`loadCacheLru` 会用现存键重建账本（`:1035-1039`）。一旦新增备份/临时键（如 `<key>.__pre_enc_plain`、`<key>.__tmp`），会被误当成「一个会话」进而污染账本、并可能被 `dropCachedConversation` 误删（`:1069-1080`）。**必须同步扩展排除规则**（账本键 + 备份后缀 + 临时后缀）。
- `hasCachedConversation` 同样只查主键（`:1090-1096`），排除规则要复用同一份常量，不要各写一份。
- `storageUsage` 的分组靠前缀（`storageUsage.ts:57`、`:65`），备份键会落进同一组——可接受（它们确实占字节），但组名要改（§2.1）。
- `StorageUsageCard` 的清理目标按前缀匹配（`StorageUsageCard.tsx:198`），会把备份键一起删掉。这正是期望行为，但确认框文案要说明「一并删除迁移备份」。

## 5. 性能预算

### 5.1 可测指标

| 编号 | 指标 | 定义 / 测量点 | 目标（推荐值） | 不达标降级 |
|---|---|---|---|---|
| M1 | 单条落定消息的加密增量 | `append` 内新增的 encrypt 段 + `setItem` 增量，p95 | ≤ 2.0 ms（单条 ≤2KB） | L1：仅对自己发出的消息立即落盘，收到的消息 500ms 空闲批量落盘 |
| M2 | 单会话冷读 | 首次 `get(convId,msgId)` 的耗时（应只解 1 条） | ≤ 1.0 ms | 若退化成全量解密则改回定点解密（不得整数组解） |
| M3 | `chains` 写入（含自校验） | `saveChains` 全段 p95 | ≤ 3.0 ms（约 80KB 密文 + 1 次解密比对） | L2：自校验降为「本会话前 3 次 + 每第 50 次」，并在文档标注风险 |
| M4 | 迁移单会话 | 500 条全量转密文 | p95 ≤ 30 ms（分 10 批） | 降低每批条数（50 → 20），或推迟到下次空闲 |
| M5 | 首启迁移总时长 | 打开应用后 10s 内累计 | ≤ 1.5 s，且不产生 >16ms 的主线程长任务 | 只迁当前会话，其余靠 P3 清理 |
| M6 | localStorage 字节增长（msgCache 组） | `measureStorageUsage` 前后对比 | ≤ +55% | 若逼近配额 ⇒ 走 §5.3，或提前触发 P4（换存储层） |
| M7 | localStorage 字节增长（加密会话组） | 同上 | ≤ +40%（信封头 + base64） | 无（很小） |
| M8 | 热路径 IPC 次数 | 每条消息的 `sendSync` 计数 | 2 次（1 加密 + 1 缓存条目加密），读侧 0 次 | L1 批量 |

**测量方法**：在 `msgCache.append`、`saveChains`、迁移批次三处埋 `performance.mark/measure`，用 `__HEMING_PERF__` 开关（仅 dev 与测试构建启用，生产零开销）；脚本用 500 条消息回放（复用 `ChatPage.test.tsx` 现有夹具，`:288` 那段清理逻辑正好可复用）；对照组为 `d.54.2.17.0` 的同一脚本。**所有目标值目前是量级估算，必须在 P1 第一步实测后回填**（见 §10 待核实）。

### 5.2 基线假设（写清楚，避免把估算当实测）

- 链状态 80KB：`msgKeys` 窗口 1000 条 × 约 60 字节（key 为序号、value 为 32B 的 base64）+ `opened` 1000 条 × 约 8 字节。
- 缓存单条 400B：`CachedMsg` = id(36) + senderId(36) + at(13) + `PlainEnvelope` JSON。
- DPAPI 吞吐按「与 AES 同量级或更慢一个数量级」保守估；这正是 M1/M3 必须在真机实测的原因。

### 5.3 配额：本方案唯一实质缺陷与处置

现状已经贴着上限：20 个会话 × 500 条 × 400B ≈ 4MB，而 Chromium localStorage 同源预算保守下限是 5MB（`storageUsage.ts:22`）。加密后约 ×1.5 ⇒ 可能越界。处置顺序：

1. **预检**：迁移前用探针实测真实配额（`storageUsage.ts:269-320`，注意它「只在用户点重新检测时调用」的既有约束 `:264-265`；迁移场景可放宽为「每个版本一次」）。
2. **追加时的配额兜底**：`append` 捕获 `QuotaExceededError`（判定函数已有 `storageUsage.ts:322-327`）→ 按 LRU 淘汰**最久未用的一个会话**（复用 `dropCachedConversation`，`:1045-1053`）→ 重试一次 → 仍失败则内存保留 + 可见「未落盘」。
3. **降级阶梯**（按序，前三步自动执行，第四步需拍板）：
   - L1：缓存条目延迟落盘（仅对可再生的收到消息；自发消息不延迟）。
   - L2：链自校验降频（见 M3）。
   - L3：暂停缓存加密（保持明文 + 状态卡如实标注），只保留链加密。
   - L4（需产品拍板，见 §9 Q2）：降 `CACHE_CAP`/`MAX_CACHE_CONVERSATIONS` 换空间——**会永久丢历史正文**，默认不执行。

## 8. 明确不做

1. **不搬到 IndexedDB / 主进程文件**（方案 B/C/D）：安全收益为零，工程代价与回滚风险显著更高（§3.4）。配额真成瓶颈时单独立项。
2. **不加密 `heming.e2e.deferred.*`**：内容已是对端 E2E 密文（`e2eSession.ts:11`、`:252-259`），加密只增复杂度。
3. **不加密 `heming.msgCache.lru.v1`**：仅会话 ID 与时间戳，属服务端可见元数据；收益低于维护成本。
4. **不改协议常量**：`CACHE_CAP`（500）、`WINDOW`（1000）、`DEFERRED_CAP`（50）、链轮换阈值（100 条/24h）都不动——它们是 E2E 设计的一部分（`e2eSession.ts:42-47`），改它们会改变协议行为，不属于「加密」这一轮。
5. **不做密钥导入/导出/托管/恢复**：会新增一条明文外流路径（与 d.36 `:138` 同口径）；丢失即丢失。
6. **不做内存明文清零**：JS 无可靠清零语义，做不到就不承诺。
7. **不做浏览器端的「自行加密」**：没有系统安全存储就没有密钥保护，用固定密钥/口令派生都是假装加密（`secureStorage.ts:12-13` 的既定态度）。
8. **不动 HITL / 红线 / CSP**：CSP 是 ②-6 的另一轮；本轮只加存储形态。
9. **不给主进程新增任何网络能力**：`secret-store.js` 的结构性断言（`secret-store.test.js:88-91`）继续保持，新增批量函数一并纳入同一断言。
10. **不重写 `msgCache` 的淘汰策略**：只增加「配额满时淘汰一个最久未用会话再重试」，LRU 口径与 20 会话上限不变。

## 10. 待核实 / 未实测清单

以下项本文按代码推断给出，实施前必须核实或实测，**不得当成已验证结论**：

1. **DPAPI 实际耗时**：M1/M3 的目标值来自量级估算，无真机数据。P1 第一步就要建基线（同一脚本、同一机器、500 条回放）。

3. **`peek`/`remove` 的生产调用点**：全仓 grep 只在测试里出现（`msgCache.peek`、`msgCache.remove` 无生产调用），是否有计划中的预览功能会用到 —— 待与前端确认；若有，`get()` 之外还要保留整数组读的能力。
4. **`e2eSession.test.ts` 里依赖「`openMessage` 后同步读 `msgCache.list`」的用例精确条数**：grep 命中 17 处 `msgCache.list`，其中多少会在有桥路径下受影响，实施时逐条确认（这决定「方案 A 的测试改动量」估算精度）。
5. **`chains` 稳态体量**：80KB 是按窗口 1000 条推算，需用真实会话（长对话）取一次实际值，因为它直接决定 M3 是否达标。
6. **`app://` 上的 `fetch` 与同源判定**（仅方案 B 相关，本轮不做）：`main.js:66-71` 注册为 `corsEnabled: true`，若将来走 B 需实测跨 scheme fetch 的凭据与缓存语义。

## 11. 拍板记录（Lead，2026-11-02）

| 问题 | 决定 | 理由 |
|---|---|---|
| Q1 链加密失败时 | **fail-open**：保留明文、内存继续可用、设置区「密钥存储」卡如实点名「未加密」 | 链是解密能力的唯一来源，加密失败若拒绝写盘等于把新消息也锁死；与 d.36「失败保留明文 + 可见提示」同一口径 |
| Q2 配额不足时 | **保持明文、不截短缓存** | 自发消息不可再生（设计稿 B1），任何「腾空间」的自动动作都可能永久丢正文 |
| Q3 迁移期明文备份 | **保留一个完整版本**，键名 `<键>.__heming_plaintext_backup`，幂等、不二次备份；P3 阶段清理 | 迁移期必须可回退；保留到下一个完整版本足够覆盖现场问题，又不会长期留明文 |
| 实施顺序 | P1 消息缓存（web 侧）→ P2 棘轮状态 → P3 清理旧明文；每阶段独立发布 | 与设计稿 §7 一致 |
| 本轮不做 | IndexedDB / 主进程文件搬迁、批量 IPC 通道、ChatPage 调用点改造（由 Lead 在 integration 改） | 前两项安全收益为零却要异步化 E2E 链；后两项与他轨在途文件冲突 |

**已实施补充口径（P1，2026-11-02）**：`chains` 写入自校验失败时**不回退旧盘值**，改为 fail-open **保留新明文值**——链状态是单调推进的，回退会让下一条消息复用已用过的 msgKey（比明文降级危险得多）。失败同时进入 `plaintextKeys`（设置区点名该键）并留一条可诊断日志；明文旧值在任何加密覆盖前先写入 `<键>.__heming_plaintext_backup`（幂等，Q3）。后续维护者不要按 §9 Q1 的字面「回滚为旧值」改回退实现。
