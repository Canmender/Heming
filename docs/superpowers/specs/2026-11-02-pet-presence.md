## 0. 问题

桌宠现在只有两种信息来源：**用户点它**，和**有新消息**。除此之外它对平台一无所知——
晨报生成了它不知道，任务跑完了它不知道，日程快到了它也不知道。

而这三件事恰恰是「它在场」最有价值的时刻：不是又一个聊天入口，而是**它替你先看一眼**。

但「什么都推给它」比不推更糟。桌宠是常驻在桌面上的东西，任何一条不合时宜的提示都会变成干扰。
所以这一期的真正难点不是"怎么推"，而是**谁来决定该不该开口**。

---

## 1. 决策

### 1.1 事件由**已有模块**产出，桌宠只负责表达

不在桌宠里重新判断"晨报该不该发"——那套逻辑（静默时段、每日预算、去重账本）d.48 已经实现且有测试。
桌宠接的是**已经决定要发**的那一步，只是把出口从"通知中心"扩展到"也可以让桌宠说"。

对应到代码：`window.__heming_pet.emit(payload)`，payload 契约见 `lib/petEvent.ts`。

### 1.2 开口需要「预算」，且与通知中心共用

一条简报**要么**进通知中心**要么**让桌宠说，不该两边都来一次。
所以不新增一套配额，而是把桌宠的"说"注册成通知中心的一个**送达渠道**：

```
产生一条简报
  → 通知中心判断：静默时段？今日预算用完？重复？
      → 要发 → 选渠道：主窗口在前台 → 通知中心
                        主窗口不在前台 / 已关闭 → 桌宠
      → 不发 → 丢弃（桌宠不说话）
```

判据是「用户此刻能不能看到主窗口」。桌宠的定位是**主窗口不在时的替身**，不是并列的第二个提醒器。

### 1.3 三种「说」的强度，按打扰程度分档

| 档位 | 形态 | 用于 | 是否打断 |
|---|---|---|---|
| 静默 | 只在角标/气泡上累加数字 | 未读消息 | 否 |
| 轻提示 | 气泡显示 8 秒后收回，无动作 | 任务收尾、日程临期 | 否 |
| 开口 | 气泡 + `speaking` 姿态 + 口型，主动说一句 | 晨报、用户主动问 | 半打断（有时长上限） |

「开口」档有硬约束：**单次不超过两句**（约 60 字），因为它是模型生成而非模板拼接，
不设上限就会变成在桌面上念文章。

### 1.4 错过的事件不补发

主窗口关闭、桌宠隐藏、网络断开期间产生的事件**直接丢弃**，不做队列。
理由：简报与提醒的价值随时间快速衰减，十分钟前的「日程 5 分钟后开始」补发出来是负价值。
用户想要完整信息，打开主窗口看通知中心即可——那里是**事实**，桌宠只是**当场**的提醒。

## 2. 数据边界

| 数据 | 处理 |
|---|---|
| 事件 payload | 只在内存流转，不落盘 |
| 送达记录（哪条已说） | 复用通知中心已有的去重账本，不新建 |
| 桌宠生成的那句话 | 与对话同口径：**不写会话、不进消息列表、不落明文缓存** |
| 静默时段 / 预算 | 读 d.48 的 `heming.staff.*`，不复制一份 |

---

## 3. 明确不做

- **不做语音播报**：TTS 需要供应商与音频管线，另立规格（接口位置见 `docs/PET.md` §4.4）。
- **不做多形象 / 换装 / 亲密度**：仍只支持「内置默认 + 手动指定」。
- **不做桌宠自主发起对话**（没有触发源就找用户聊天）：那是另一类产品，且极易变成打扰。
- **不做跨设备同步**：桌宠状态是本机的。
- **不做 macOS 适配验证。**

---

## 4. 验收形态

1. **晨报**：模拟主窗口关闭 → 幕僚生成晨报 → 桌宠气泡说一句（≤60 字），8 秒后收回，不进消息列表。
2. **任务收尾**：任务成功/失败各一次 → 气泡措辞分别为「完成了：X」「没成功：X」。
3. **不重复**：同一条简报在主窗口前台时只进通知中心，桌宠不说话；切到后台后不补发。
4. **静默时段生效**：静默时段内产生的事件，桌宠全程不出声。
5. **不打断对话**：桌宠正在与用户对话（`speaking`）时，新事件排队到该轮结束后再决定是否显示。
6. **畸形事件**：手工 `emit({ kind: "speak", text: "" })` → 无任何反应、不报错。
7. 门禁全绿，`docs/PET.md` 的 §4.3 从「暂无生产者」更新为实际来源列表。

---

## 5. 风险

- **打扰**：这是本期最可能失败的地方。缓解手段是 1.2 的渠道互斥 + 1.3 的强度分档；
  但仍需一次真机试用（连续挂机一天）来校准"一天说几次算合适"。**建议先按每天 ≤3 次开口**。
- **重复**：如果通知中心与桌宠各判一次，会出现"两边都发"。1.2 要求单一判据，实现时不要把判断散在两处。
- **模型成本**：「开口」档要调模型，频率必须被预算卡住，否则会在后台持续产生 token 消耗。
- **超时**：模型生成超过 8 秒时，气泡已收回而文字才到——需要在生成前先占位（显示"…"）。

---

## 6. 需要先定的问题

1. **渠道互斥的判据**用「主窗口是否可见」还是「主窗口是否在前台（focus）」？
   后者更准，但对多显示器场景会误判（用户看着副屏也算后台）。
2. **开口档的一天上限**取 3 次还是按简报类型分别限（晨报固定 1 次 + 提醒若干）？
3. **桌宠隐藏时的事件**：直接丢弃（1.4 的立场）还是写入通知中心等用户打开？
   两者会改变"关掉桌宠"这个动作的语义。
4. **是否允许用户手动触发**「让它说一句」（托盘菜单）？如果允许，它算不算预算？

## 7. 实施记录（第二波，d.58.x）

### 7.1 §6 待定问题的落地选择

| 问题 | 选择 | 理由 |
|---|---|---|
| 渠道互斥判据 | **主窗口是否前台**（`document.hasFocus()` + 可见），并在主进程 `pet:emit` 里用 `main.isFocused()` 再判一次 | 前台判据比「可见」更贴近「用户此刻能不能看到主窗口」；主进程复判是因为跨进程边界不信任渲染层。多显示器下副屏场景的误判可接受（最坏是多一次通知中心、少一次桌宠说话）。 |
| 开口档一天上限 | **不做独立的每日开口预算**；沿用通知中心已定的静默时段/每日预算/去重账本，桌宠只加「同一事件 10 分钟一次 + 10 分钟最多 3 次」的频控 | spec §1.2 要求单一判据；再建一套预算必然出现「两边都发/两边都不发」。 |
| 桌宠隐藏时的事件 | **直接丢弃**（不写通知中心、不排队） | 通知中心里本来就有这条事实，用户打开主窗口能看到；桌宠只是「当场」的提醒。 |
| 托盘手动「让它说一句」 | 本轮不做（不在本期验收内） | 与「不做自主发起对话」一起留给后续。 |

### 7.4 已知边界

- 频率是否合适仍需真机试用校准（spec §5）：现有硬上限是「同事件 10 分钟一次 + 窗口内最多 3 次」。
- 幕僚简报的 `speak` 文案来自 `summary`（规则模式是计数句、LLM 模式是模型总结），已截断到 ≤60 字；
  若将来 summary 里出现正文级内容，属于 d.48 的净化问题，不在本轮重复处理。
- 桌面系统通知仍由既有 `notifyDesktop`（主窗口失焦时）负责；桌宠与系统通知可以同时出现，
  但比通知中心多了「同事件 10 分钟一次」的桌宠频控。
