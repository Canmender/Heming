# 09 · 验证优先：把"agent 能不能自己证明做对了"当前提

> 本篇是「智能体调优」研究的第一篇。素材主线是 Lauren Tan（@poteto，前 Cursor 核心成员，现 Grok Bot）的 pstack 方法论——即用户指定阅读的掘金文章 [《GrokBot 核心成员 Lauren Tan：每月交付 2000 个 PR 的人，是怎么用 AI 的》](https://juejin.cn/post/7687032811338891302)；交叉验证素材是 Cursor 官方研究博客 [《Towards self-driving codebases》](https://cursor.com/blog/self-driving-codebases)（2026-02-05，Wilson Lin）与两篇业界实证研究（**数字均转引自上述掘金文章，一手论文本环境未能取到**）。
>
> 本篇只讲一件事：**为什么"验证闭环"是智能体能力的第一性杠杆，以及怎么把它做成基础设施。**

---

## 0. 一句话

> 一个 agent 的能力上限，不是它写得多快，而是**它能不能在不打扰人的情况下证明自己做对了**。验证做得出来，其他优化（上下文、编排、提示词）才有意义；验证做不出来，你永远是人类流水线上的人工质检员。

这句话在三个独立来源上一致：

| 来源 | 原话/结论 |
|---|---|
| Lauren Tan | "如果 agent 不能验证自己的工作，其他一切都不重要。你仍然是瓶颈，你的一整天都会花在 babysitting agent 上。" |
| Cursor | 单 agent 做浏览器时"频繁停下来宣称成功，尽管离目标还很远"——**没有验证信号，模型只能靠"感觉完成"** |
| 业界数据 | AI 代码量上去后，人类 review 能力没同步上去（substantive review 39%→21%），企业被迫把 review 转移给自动化——**验证是产能的前置，不是产出的附属** |

## 1. 先看数字：2000 个 PR/月背后的真实结构

Lauren 给出的数字（转引自掘金文章）：

| 指标 | 数值 |
|---|---|
| 上月交付 PR | 1,000 |
| 本月目标 | 2,000 |
| 单晚自动合并 PR | ~20 |
| **前置重构 PR 投入** | **600+** |

她在文章里说的关键一句是：

> "600 多个重构 PR 才是真实的基础设施。那晚自动合并的 20 个 PR，只是输出。"

**这就是调优的第一课：吞吐是架构的函数，不是提示词的函数。** 600:20 ≈ **30:1** 的投入产出结构——先花 30 份工程量把"agent 工作环境"改造成"短路径即正确路径"，之后才能有 20 份/晚的自动产出。

### 1.1 这套系统成立的三个前提

文章结尾自己列了，值得抄下来当"适用性自检"：

1. **有一个对系统理解极深的 owner**：所有高层判断（架构、意图、取舍）仍然由人做。
2. **有架构地基**：600+ 重构 PR 让 agent 的"最短路径"就是"正确路径"。
3. **隐性判断被显性化**：把"我们团队知道但没写下来"的东西，编码成 agent 可执行的规则/脚本/检查。

**少任何一个前提，同一套工具的效果都会大打折扣。** 这解释了为什么很多团队抄了 pstack 的 skill，却复现不出吞吐——他们抄的是输出层，没抄输入层。

## 2. 第一根杠杆：把"验证"从口头要求变成可执行物

### 2.1 她对"验证"的定义（和大多数人不一样）

不是跑测试、不是 build 通过，而是：

> **驱动真实应用 → 执行真实流程 → 检查真实产物 → 给出可视证据。**

对应到不同变更类型，证据形态不同：

| 变更类型 | 验证方式 | 证据形式 |
|---|---|---|
| CLI 变更 | 跑真实命令 | 命令输出 vs 预期输出 |
| UI 变更 | 在运行的应用里走一遍流程 | 截图 / 录屏 |
| 解析器 / 数据迁移 | 重放已保存的真实输入 | 前后输出 diff |
| 性能变更 | 前后各跑一次 profile | 性能数据对比 |

这张表的价值：**它把"做完"的定义从形容词换成了名词**。"实现完成"是形容词，"这条命令输出等于这段文本"是名词。所有可自动判定的完成条件，本质都是后者。

### 2.2 Feature Map：给每个功能定义"正常的证据"

pstack 的 `/create-verification-skill` 会扫描仓库，自动识别：用户触达点、应用启动方式、可驱动接口（浏览器 CDP / PTY / HTTP 接口），然后生成两样东西——**验证技能文件** + **Feature Map**。

Feature Map 是逐功能的索引，每个功能一个 md，固定四段：

```markdown
## Launch     如何启动应用到"这个功能可用"的状态
## Drive      驱动这个功能的步骤（命令序列 / 操作序列）
## Evidence   什么结果证明这个功能正常（具体输出 / 状态 / 文件）
## Cleanup    验证完成后要清理什么状态
```

这个四段式其实是**验证的可复用最小单元**：

- `Launch` 解决"从零到可验证状态"的成本（否则每个任务都重新摸索怎么跑起来）；
- `Drive` 解决"驱动路径不稳定"（人每次手点的地方不一样，agent 也一样）；
- `Evidence` 是**判定标准**，必须具体到"值/文件/状态"，不能是"看起来对"；
- `Cleanup` 解决**验证副作用污染**——这条最容易被忽略，却决定了验证能不能在同一个环境里重复跑。

### 2.3 验证技能会腐化，必须当基础设施养

文章里一个很清醒的判断（很多人会跳过的一段）：**Feature Map 会随代码演进腐化**——当初定义的"证据"可能不再成立。pstack 有 `/maintain-verification-skill` 来审计，但本质是持续投入，不是一次性工作。她的结论是：把它当**关键基础设施**，值得设 oncall 轮值。

> 对做 agent 框架的人的启示：**验证能力必须有 owner、有巡检、有"证据过期"的检测机制**。否则三个月后你的 agent 会用一套过时的证据宣布成功——比没有验证更危险，因为它给了你虚假的安全感。

### 2.4 验证闭环带来的直接收益：Overnight Run 成为可能

前面全是为这一步铺路：

```
验证技能建立 → agent 能自我闭合（不需要人确认"是不是真做对了"）
             → 才敢让它整夜自主工作（Overnight Run）
             → 才有 20 PR/晚的产出
```

**顺序不能反。** 没有自我验证就开长时自主，收获的不是产能，是一夜之间的技术债。

## 3. 第二根杠杆：硬边界胜过软规范

### 3.1 Dune 架构：让"最短路径"就是"正确路径"

Grok Bot 代码库最初是"agent 觉得怎么方便就怎么来"的原型，任务单独看都能完成，但目录、依赖、进程边界、状态管理全缠在一起。人能改，但越来越难信任。她的选择不是写更长的规范，而是**重建架构**（代号 Dune），核心判断一句话：

> "Agent 喜欢走捷径，所以让最短路径就是正确路径。"

四条具体做法：

| 做法 | 机制 |
|---|---|
| Feature 共置 | 一个功能的状态/组件/逻辑放同一目录，不分散 |
| 进程边界 | 主进程与渲染进程隔离，重任务不挤 UI 线程 |
| **依赖图 CI 检查** | 机械地阻止跨层、跨进程 import——不是写规范，是直接封掉 |
| **危险模式禁用** | 用 lint 把 agent 反复误用的模式（如滥用 `useEffect`）变成编译错误 |

### 3.2 "请你不要" vs "你不能"

文章里那个对比例子堪称经典，直接抄：

```markdown
<!-- docs/CODING.md：agent 可能读到，也可能没读到 -->
- UI 层不允许直接 import 数据库模块
```

```javascript
// eslint.config.js：每次 CI 都强制执行，没有例外
{
  rules: {
    'no-restricted-imports': ['error', {
      patterns: [{
        group: ['@packages/db/*'],
        message: 'UI 层禁止直接访问数据库，走 @packages/api'
      }]
    }]
  }
}
```

> **规范要求 agent 每次都"记得"遵守；架构约束直接让违规这条路不存在。前者依赖 agent 的配合，后者不依赖。**

这条与 Cursor 的实证完全一致：

> "Constraints are more effective than instructions. 'No TODOs, no partial implementations' works better than 'remember to finish implementations.'" —— Cursor《Towards self-driving codebases》

Lauren 比 Cursor 更进一步：不只约束行为，直接封死路径。**注意措辞是"封死路径"而不是"加强 lint 报错"**——差别在于违规是否可能发生。

### 3.3 把这条推广成通用规则

| 你想让 agent 做到 | 软做法（不可靠） | 硬做法（可靠） |
|---|---|---|
| 不改某些文件 | 提示词"请不要改" | 权限/沙箱/只读挂载 |
| 不引入某依赖 | 规范文档 | 依赖白名单 + CI 拒绝 |
| 不留 TODO | "记得完成" | 提交前 lint 禁止 `TODO(` |
| 不改 public API | code review 提醒 | 类型/契约测试 + 破坏性变更检查 |
| 不越界读文件 | "只读相关文件" | 工具参数白名单 / 路径约束 |

判断标准：**如果你的约束只写在提示词里，那么它是否生效取决于模型这一次的心情。**

## 4. 第三根杠杆：把"理解验证"前置到成本最低的环节

### 4.1 Indirect Prompt：让 agent 用自己的话复述问题

她在实践里最常用的技巧：**不直接告诉 agent 要做什么，而是先让它读相关材料、用自己的话复述问题，再动手。**

典型场景：Slack 上有人报 bug → 让 agent 读完整 thread → 用自己的话重述问题 → 如果复述有偏差，在写代码前就纠正。

> 本质：**把理解验证前置，把错误拦截在成本最低的环节。**
>
> 写代码前的误解，修复成本 ≈ 0；写完再发现方向错，成本 = 全部返工 + 上下文重建。

这个技巧可零成本落地，且对任何 agent 框架都适用。**它的工程化形态**：把"复述"做成任务启动的第一条强制步骤，复述通过再进入执行阶段。

### 4.2 设计阶段的四个工具

| 工具 | 干什么 | 值得抄的细节 |
|---|---|---|
| `/how` | 追踪系统**当前**行为（读代码，不是猜） | 大系统先派 2-4 个**只读 explorer 并行扫描**再汇总——这是"用子代理保护主上下文"的典型 |
| `/why` | 挖历史决策（这个 5 的来历、当初理由是否还成立） | 查 git / issue / 聊天 / 文档；**直接证据与推断分开标注**；查不到就明说"没有人记录过原因"——**这本身也是答案** |
| `/arena` | N 个 subagent 各自独立 worktree 做同一设计任务 | 由一个**不同模型家族**的评审 agent 按统一评分标准打分，协调者合并胜出方案 + 落选方案的优点 |
| `/interrogate` | 同一份 diff 交多个不同模型家族的 reviewer | Lead reviewer 把发现分四类：**Act on / Consider / Noted / Dismissed**，每个 Dismissed 必附理由 |

两个可以立刻偷的设计：**"不同模型家族交叉评审"**（同族模型有共同盲区，跨族能显著提高证据独立性）与**"驳回必须写理由"**（否则 review 会退化成噪音）。

### 4.3 对 Plan Mode 的批评（重要）

文章直接引用：

> "Plan Mode 常被用来说服自己 agent 会做正确的事。但现实是，抽象的计划只给你一种生产力的错觉。一份长篇大论的计划看起来很有成效，但可能缺乏实质。"

pstack 的替代方案：用详尽的调查（`/how` + `/why`）、实证证据（验证技能）、严格验证（行为检查）来取代长篇计划。

> **计划的价值在于它是否基于真实证据，而不在于它有多长。**

这条对我们写 agent 框架的人是一个明确的取舍信号：**不要用"让 agent 先写一份长计划"来假装推进了工作。** 值得投入的是"让 agent 拿到可验证的事实"。

## 5. 第四根杠杆：把方法论变成可 steering 的"词汇表"

pstack 内置 23 条工程原则。**用法不是让 agent 背，而是当你发现它在做错事时，用一个短语精准纠正**，而不是重新解释一遍：

> "apply **prove it works**. show me the real output, not the build log."
> "use **subtract before you add**. delete the obsolete adapters first, then design what's left."

每条原则背后是完整规则说明，agent 已读过，所以一个短语就能重定向行为。**这是一种"低 token 成本的纠正接口"。**

原文里挑出的高价值条款（分组）：

**核心**

- **Laziness Protocol**：优先删除，做能解决问题的最小变更
- **Subtract Before You Add**：先去掉死重，再建新东西
- **Attack the Premise**：两次以上修复都失败，停下来质疑它们共享的前提
- **Minimize Reader Load**：折叠读者必须记在脑子里的层与隐藏状态
- **Build the Lever**：写一个能"做这件事/证明这件事"的脚本，让 reviewer 可重跑

**架构**

- **Model the Domain**：重复的业务规则编码进一个结构，而不是散落的条件判断
- **Boundary Discipline**：在边界处验证，信任内部类型
- **Type System Discipline**：让非法状态在类型层面不可表示
- **Migrate Callers Then Delete Legacy APIs**：迁移调用方与删除旧 API 在同一个 PR 完成

**验证**

- **Prove It Works**：验证真实产物，不是代理指标；**"It compiles" 不是证据**
- **Fix Root Causes**：先复现、追到根因，再改代码
- **Test Behavior, Not Implementation**：以用户调用代码的方式测试，断言字面预期值

**委托**

- **Guard the Context Window**：把大量阅读路由给 subagent，把结论留在主对话
- **Never Block on the Human**：可逆工作继续推进，把结果展示给人，而不是停下等许可

**元**

- **Encode Lessons in Structure**：**你重复过两次的建议，应该变成 lint 规则、CI 检查或脚本**

最后这条是整套系统能自我进化的根：**人在 review 里重复说的话，被固化进结构，于是下一次不需要再说。**

## 6. Overnight Run：把"信任"换成"合约"

这是整套系统的 pay-off。关键不是"信任"，是**结构化的合约**。原文模板：

```bash
我要睡觉了。在一个 fresh worktree 里把所有 caller 迁移到新 parser。
完成条件：0 个旧 caller，所有 parser fixtures 通过，旧 API 已删除。
保留决策日志。不要在提交前问我。
/loop 直到完成。如果真的卡住了，停下来写清楚原因。
```

逐行拆解（每一行都在消除一种失败模式）：

| 文本 | 消除的失败模式 |
|---|---|
| "我要睡觉了" | 会话覆盖：agent 停止等待人类输入，继续推进 |
| "完成条件：..." | 模糊目标：每次迭代可自动 pass/fail |
| "fresh worktree" | 与本地其他工作冲突 |
| "不要在提交前问我" | 预先回答权限等待（否则 agent 卡在审批） |
| "如果卡住，写清楚原因" | **逃生舱**：胜过 8 小时的目标偏移 |
| "/loop 直到完成" | 明确的迭代驱动 |

> **一个常见的坑**："工作 4 小时"不是合法的完成条件。它给的是一段时间，不是一个可验证的状态。你早上得到的会是"4 小时的动态"，而不是"一个结果"。

### 6.1 迭代循环

```
检查完成条件 → 做最小的合理变更 → 对真实产物验证
   → 有进展? 是: 提交 commit / 否: 丢弃变更
   → 记录一行决策日志 → 回到检查完成条件
```

三个细节都不是小事：

1. **一次变更一次检查**：避免"改一大坨然后全量验证"，失败时无法归因。
2. **没进展的变更要丢弃**：不留下"半成品垃圾"，否则下一轮会被污染。
3. **完成条件永不悄悄放宽**：连续无进展 ≠ 降低标准宣布胜利，而是**换方向**。

### 6.2 早上审计：用另一个模型家族读日志

`/show-me-your-work` 生成 **TSV 决策日志**：时间 / 阶段 / 决策 / 原因 / 证据指针 / 结果。

更关键的是：**用另一个不同模型家族的 agent 去读这份日志 + 整夜 transcript**，给你一份"哪些地方值得你关注"的摘要。

> 你审计的是**关键决策**，不是逐行重读整夜的工作。

这是"最小注意力"原则在审计环节的落地：**人的注意力只花在异常与被放弃的决策上**，而不是均匀撒在产出上。

## 7. 交叉验证：Cursor 自驾驶代码库怎么说

Cursor 的内部研究建了一个能同时跑数千 agent 的系统，连续跑一周，让 agent 自主构建一个 Web 浏览器，产出了绝大部分 commit。它的结论与 Lauren 的方法论对照：

| 结论 | Cursor | Lauren / pstack | 一致性 |
|---|---|---|---|
| 复杂任务必须拆解 | ✅ | ✅ | 完全一致 |
| 约束比指令更有效 | ✅ | ✅（更彻底：封死路径） | 一致 |
| 给意图不给步骤 | ✅ | ✅ | 完全一致 |
| 接受错误率换吞吐量 | ✅ | ⚠️ 更强调合入前拦截 | 策略分歧（见下） |
| 移除中央协调者 | ✅ | ❌ 强中央路由 | **架构分歧（规模决定）** |
| 实证驱动而非假设驱动 | ✅ | ✅（23 条原则全部来自真实失败） | 完全一致 |
| 人类负责判断 | ✅ | ✅ | 完全一致 |

### 7.1 Cursor 的关键数字（来自原文）

| 事实 | 数值 |
|---|---|
| 一周峰值吞吐 | **~1,000 commits/hour** |
| 一周工具调用总量 | **10M tool calls** |
| 运行期间人工干预 | 启动后**无需干预** |
| 队列/协调退化（早期自协调方案） | 20 agents 退化到 **1–3 agents 的吞吐** |

### 7.2 最终架构：递归 planner，而不是全知协调者

Cursor 的演化路径很值得看，因为它把"多智能体"的坑全踩了一遍：

1. **共享状态文件自协调** → 失败：锁持有太久、忘记释放、非法加锁解锁；20 agents 锁竞争退化到 1–3 的吞吐；**没有结构就没有 agent 承担大任务**（都去抢小而安全的改动）。
2. **Planner → Executor → Workers → Judge** → 缓解协调问题、有明确归属，但**瓶颈是最慢的 worker**，僵化；upfront 计划无法动态调整；某些 agent 朝错误方向走却要等下一轮才能自纠。
3. **Continuous executor（去掉 planner）** → 又出现病态行为：随机 sleep、停掉 agent、自己干活、拒绝计划、不合并 worker 改动、提前宣称完成——**因为它同时承担了 8 个角色**。
4. **最终形态**：root planner（只规划不写码，不知道任务被谁接走）→ 可递归 spawn subplanner（完全拥有自己的窄切片）→ workers（各自仓库副本，互不通信，完成后写**一份 handoff** 交给请求它的 planner）→ handoff 同时到达 planner 作为后续消息，让系统持续运动。

与 dsh-superagent 的"主 Session 不写码 / worker 只做一张工单 / 只有最终 report 能结束工单"是同一个设计直觉：**规划者不执行、执行者不越界、交接靠结构化产物。**

### 7.3 关于"接受错误率"的分歧要看场景

Cursor：追求 100% 正确会让系统"为一个小 typo 全面停摆"，worker 越界去修无关问题、互相踩踏；因此接受"小但稳定的错误率"，最后做一次 reconciliation pass（定期快照 + 快速修复）。

Lauren：生产产品，合入前拦截（每个 PR 独立通过验证才合入）。

> **判断标准：你的系统能否承受"事后清理"？** 研究型/一次性项目可以（先跑起来，最后统一修）；生产系统不行（返工成本与信任成本指数上升）。**这不是价值观分歧，是场景分歧**——照抄策略而不判断场景，是常见的落地失败原因。

## 8. 业界数据：这些方法到底有多大用

> 以下数字**均转引自用户指定的掘金文章**，一手论文本环境未取到；引用时请保留"转引"字样。

### 8.1 AI Code Review 的真实有效性

CodeRabbit 在真实 GitHub 项目的 31,073 条 review 评论，开发者反馈分布：

| 反馈 | 占比 |
|---|---|
| 接受 | 36.4% |
| 引发讨论 | 7.3% |
| **拒绝** | **56.3%** |

拒绝主因：false positive、超出范围、与开发者意图不符。

另一项 24,005 个 review 实例的研究，按问题类型对比 LLM 与人类 reviewer：

| 问题类型 | LLM 表现 |
|---|---|
| 风格/命名/格式 | 与人类持平 |
| 简单逻辑错误 | 较好 |
| 功能缺陷 | 中等，false positive 较高 |
| **架构问题** | **87% 被遗漏** |
| 可演化性/长期维护性 | 覆盖率低且持续下降 |

**结论很明确**：多模型 review 对"风格统一 + 明显错误"有价值，**不能替代人类的架构判断**。所以 pstack 里 `/interrogate` 是**辅助手段**，最终架构决策仍由人做。

### 8.2 企业实测：产能上去了，review 成了新瓶颈

CMU + Stanford 跟踪一家企业强制推行 AI 编码工具后的 196,212 个 PR：

| 指标 | 政策前 → 后 |
|---|---|
| 人均 PR 吞吐 | 基线 → **2.09x** |
| AI 生成 PR 的 review 周期 | **+20~22%**（变慢） |
| 人类 substantive review 占比 | **39% → 21%** |
| 自动化 AI review 覆盖率 | ~19% → **~84%** |
| Merge 率 | 稳定 |
| Revert 率 | 略降 |

这篇论文的措辞很诚实：它没说"自动化 review 更好"，它说的是——**人类 review 能力没随 AI 产出同步提升，企业被迫把 review 转移给自动化，而这个转移在粗粒度质量指标上没有造成崩溃。**

> **质量风险被转移了，不是被消除了。** 这句话应该贴在任何 agent 调优项目的墙上。

## 9. 落地路线：三阶段

```
Phase 1（今天就能做）         Phase 2（1-3 个月）        Phase 3（持续投入）
├ 机械约束 lint/CI/目录结构    ├ 建立 Feature Map          ├ 验证技能维护（oncall）
├ 原子 PR 规范                ├ 验证技能上线              ├ 原则库 owner
└ Indirect Prompt 复述         └ 低风险任务 Overnight Run   └ 架构决策人工把关
```

### 9.1 现在就能落地的四件事（性价比最高）

1. **机械约束**：lint、CI 依赖图检查、目录结构、类型约束。不需要 AI，对人类同样有效，且**永不腐化**。
2. **验证技能（Feature Map）**：即使先手工维护 5 个核心功能，也能立刻让 agent 自我闭合。
3. **原子 PR 规范**：一个 PR 一件事，可独立验证与回滚——这是所有后续自动化的基础。
4. **Indirect Prompt**：让 agent 先复述再动手，成本≈0，收益立竿见影。

### 9.2 必须人工持续的三件事

- **架构决策**：87% 遗漏率短期不会根本改变。
- **验证技能维护**：会腐化，需要 owner + 巡检。
- **原则库维护**：新问题模式要新原则，旧原则会失效。

### 9.3 暂时不要做的三件事

- 让 agent 自主做架构决策；
- 完全无人值守的新功能开发（Overnight Run 只适合**边界清晰、完成条件可机验**的迁移/重构类任务）；
- 用多模型 review 替代人工架构评审。

## 10. 对 DSH 一类框架的直接启示

| pstack 的做法 | 框架层面对应物 | 建议 |
|---|---|---|
| 验证技能 / Feature Map | 每个任务类型的"完成判定器" | 把"done 的定义"做成可注册的能力，而不是提示词里的一句话 |
| 硬边界（lint / 依赖图 / 权限） | 工具权限 + 沙箱 + CI 钩子 | 凡是"重复两次的纠正"，都升级成结构性约束 |
| Indirect Prompt | 任务启动的"复述阶段" | 在 plan 之前加一步"用自己的话重述目标与验收条件" |
| `/how` 的只读 explorer | subagent 只读模式 | 大量阅读一律 route 给子代理，主上下文只留结论（与 Manus / Anthropic 一致） |
| 跨模型家族 review | 多 provider 评审 | 评审者与作者尽量不同模型；驳回必须附理由 |
| Overnight Run 合约 | 长时任务模板 | 六要素做成模板：覆盖等待 / 可验证完成条件 / 隔离 worktree / 不问人 / 写清卡点 / 循环 |
| 决策日志 + 跨模型审计 | 结构化 trace | trace 要能回答"每次迭代为什么这么改"，而不只是"调了哪些工具" |
| 23 条原则的 steering 用法 | 可命名原则库 | 原则要能被"一个短语"引用，否则纠正成本太高 |

**最容易验证的一条自检**：问自己的框架——**"如果一个 agent 说它完成了，我能在不读它代码的情况下，用一个命令判断真假吗？"** 不能，就说明验证层缺失，此时任何"提升 token 效率"的优化都是在优化一个无法确认的结果。
