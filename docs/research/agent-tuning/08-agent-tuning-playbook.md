# 08 · 智能体调优总纲：四根杠杆、一套度量、一张落地路线

> 这份总纲回答用户的问题：**「智能体怎么调优、怎么提升 token 使用率、怎么增强任务完成效率与能力」**。
> 结论集中在这一篇；证据、原文引用与可抄的模板在六份分册（09–13），每节都标了该去哪篇看细节。
>
> 研究方式说明：本机 `web_search` 因 API Key 失效不可用（401），所有外部结论均为**直接抓取一手 URL** 得到（Anthropic / Cursor / Cognition / Manus / OpenAI / Chroma / arXiv / 掘金）；github.com 全域不可达，故 pstack 仓库、12-factor 仓库 CONTENT 标"二手，转引自掘金文章"。每篇末尾都有"未取到"清单，没有编造。

## 0. 一句话结论

> **agent 的能力 ≈ 它能否自己证明做对了 × 它每次拿到的上下文质量 × 它的工具契约有多好用。**
> token 花得少不是目标，"每一 token 都在推动一个可验证的下一步"才是目标。

三个可操作的判断，代替"感觉调优"：

1. **先补验证，再谈优化**。没有可机验的"完成"，任何吞吐/成本优化都在优化一个无法确认的结果。
2. **凡是你重复叮嘱两次以上的事，都不属于提示词，而属于 harness**（lint / CI / 权限 / schema / 工具返回）。
3. **上下文是预算，不是容器**。宁可用 3 次精准读取 + 1 次总结，也不要把 50 个文件塞进主对话。

## 1. 四根杠杆总览

```
                       任务完成率
                          ▲
        ┌─────────────────┼─────────────────┐
   杠杆A 验证闭环      杠杆B harness/工具    杠杆C 上下文与 token   杠杆D 编排与模型
   （能不能证明对）    （能不能顺手做对）    （信息密度/缓存）      （拆不拆、谁来拆）
```

| 杠杆 | 一句话 | 典型收益量级 | 主要成本 | 见效速度 | 详见 |
|---|---|---|---|---|---|
| **A 验证闭环** | 让 agent 能自己跑真实流程并比对证据 | 吞吐天花板从"人 review 速率"变成"验证速率"；Overnight Run 的前提 | 每功能一次建模 + 长期维护 | 中（1–4 周） | 09、11 |
| **B harness / 工具契约** | 工具输出精简可决策、错误可操作、非法状态不可表达 | 工具响应 token 可降 ~2/3（206→72 的同一查询） | 低，改代码即可 | 快（天） | 11、13 |
| **C 上下文与 token** | 前缀稳定（缓存命中）、只装必要信息、长任务压缩/外置 | 缓存命中 10x 价差；context editing 实测 −84% token；MCP 懒加载 −46.9% | 中（缓存结构设计） | 中（1–2 周） | 10 |
| **D 编排与模型** | 什么时候拆、拆多细、报告带什么、预算给多少 | 多智能体在合适任务上 +90.2%，但 token 是 chat 的 ~15× | 高（协调与调试成本） | 慢（依赖 A/B） | 12、13 |

**优先级建议（按投入产出）：B → A → C → D。**
理由：B 是纯工程收益、无副作用；A 是能力天花板的前提；C 需要 B 提供稳定前缀才有意义；D 的收益高度依赖 A（没有验证的多智能体 = 并行放大错误）。

## 2. 杠杆 A：验证闭环——把"完成"从形容词变成名词

> 细节见 `09-verification-first.md`（方法论 + 数据）与 `11-harness-eval.md`（协议 + 治理 + 评测）。

### 2.1 定义

**"完成"= 驱动真实应用 → 执行真实流程 → 检查真实产物 → 给出可视/可机读证据。**

不是：测试通过、编译通过、文件已创建、代码看起来对。

一个可以贴在墙上的检验题：

> **如果一个 agent 说它完成了，你能不读它写的代码、只用一个命令判断真假吗？** 不能 → 验证层缺失。

### 2.2 最小可复用单元：Feature Map 四段

每个功能一个文件，固定四段（模板可直接抄，见 11 §2.2）：

| 段 | 内容 | 常见错误 |
|---|---|---|
| `Launch` | 如何启动到"该功能可用"的状态，含就绪判据（如 `curl healthz` 返回 200） | 只写"启动命令"，不写"何时算启动完成" |
| `Drive` | 驱动步骤（命令序列/操作序列），尽量非交互 | 依赖人手点的路径，无法自动重放 |
| `Evidence` | 判定标准：退出码 / 文本 / diff / 截图相似度 / p95 数字 | 写"看起来正常"（不可机判） |
| `Cleanup` | 清理副作用（进程、数据、临时目录） | 不清理 → 第二次跑就失败 |

### 2.3 证据必须按变更类型选（不可互替）

| 变更 | 证据形式 | 失败判定示例 |
|---|---|---|
| CLI | 真实命令的 stdout/stderr vs 预期 | 输出不一致 |
| UI | 截图/录屏（必要时像素相似度） | 关键元素缺失 / 布局错位 |
| 解析器 / 迁移 | 重放已保存真实输入，前后 diff | 差异超出容差 |
| 性能 | 前后 profile 对比 | p95 劣化 > 10% |

**"测试通过"是最弱的一种证据**，它只证明你没破坏你认为重要的东西，不证明新东西能用。

### 2.4 验证会腐化，必须当基础设施养

11 篇列了 7 种腐化模式（证据过期、启动路径变了、依赖漂移、基线被 agent 悄悄更新、环境漂移、flaky、覆盖盲区）。治理要点：

- 验证技能带 frontmatter：`owner / last_verified / stability / evidence_kind`；
- `> 14 天未验证` 进审计队列，有 oncall；
- **基线变更必须独立 commit + 人工 review，禁止 agent 自更新"期望值"**（否则你会得到永久的假绿）。

### 2.5 为什么它排第一

- 有了它，才敢让 agent 整夜自主（Overnight Run），才有"600 个重构 PR 换来 20 PR/晚"的 30:1 结构；
- 没有它，团队会退化成"人工质检流水线"：AI 写 2 倍代码，人类 review 负担翻倍（实测 reviewer 负载 ×2，见 11 §7）；
- **它同时是其他三根杠杆的验收条件**：上下文优化有没有效、工具改得好不好、多智能体值不值得，都要靠"可验证的完成率"来回答。

## 3. 杠杆 B：harness 与工具契约——让"顺手"和"做对"同向

> 细节见 `11-harness-eval.md` §4（工具契约）、`13-model-prompt-memory.md` §5（结构化输出）。

### 3.1 工具返回的三条硬规则

1. **默认只返回决策所需字段**：同一查询，Anthropic 的 concise 版 72 tokens、detailed 版 206 tokens（约 1/3），信息量对决策足够。
2. **超长必须分页 + 显式标注 `truncated`**：静默截断会让模型基于残缺信息自信作答（Claude Code 默认把工具响应限制在 25,000 tokens）。
3. **错误要可操作**：返回 `{error_code, retry_with, hint}`（例如 `error: not_found; retry_with: glob("**/*.tsx"); hint: 路径区分大小写`），而不是裸 traceback。

### 3.2 能用 schema 消灭的错误，不要写进提示词

| 错误类型 | 提示词方案（弱） | schema/工具方案（强） |
|---|---|---|
| 相对路径搞错 | "请用绝对路径" | 参数只接受绝对路径（校验/自动补全） |
| 枚举值拼错 | "只允许 A/B/C" | enum 约束 + 拼错时报候选 |
| 必填项漏填 | "别忘了 xxx" | required + 缺参即拒 |
| 危险操作 | "不要删库" | 工具层拒绝 / 二次确认 / 沙箱 |

**通用原则（三家共识）：约束优于指令。** Cursor 原文："'No TODOs, no partial implementations' works better than 'remember to finish implementations.'"；Lauren 更彻底——用 lint/依赖图 CI 把违规路径**封死**，而不是反复提醒。

### 3.3 工具集收敛与命名

- 工具数量 > 15–20 时，模型选择准确率明显下降 → **按场景分组、默认隐藏冷门工具**（子代理/插件按需暴露，等价于"工具懒加载"）。
- 命名用 `动词_对象`、参数名与文档用同一套词；同一概念不要两套叫法（模型会当成两个工具）。
- 每个工具描述写"什么时候**不该**用它"——比写"什么时候用"更能减少误用。

### 3.4 harness 硬边界清单（可直接勾）

- [ ] 读类工具默认只读、写类工具必须显式路径
- [ ] shell 有超时/沙箱（前台等待 ≤ 数秒，长任务转后台 job）
- [ ] 危险命令（rm -rf、git reset --hard、force push）在工具层拒绝
- [ ] 依赖/目录边界有 CI 检查（跨层 import 直接失败）
- [ ] 提交前 lint 拦 `TODO(`、调试打印、跳过测试的标记
- [ ] 长任务有后台 job + 可查询状态（避免前台挂死浪费上下文）

## 4. 杠杆 C：上下文与 token 经济——把预算花在信息密度上

> 细节见 `10-context-token.md`（10 节，含 Manus 六条经验、缓存契约、指标）。

### 4.1 两个机制，先理解再优化

- **attention budget（注意力预算）**：上下文越长，模型对任一位置信息的有效注意力越稀释，性能随长度**非均匀**下降（context rot，Chroma 用 18 个模型、194,480 次调用验证：~113k token 与 ~300 token 的输入在同一问题上表现可差出显著幅度）。
- **KV-cache 命中率决定成本**：缓存未命中时输入 token 成本可差 **10x** 量级；而缓存是按**前缀**匹配的——**任何前缀变化（时间戳、工具顺序、动态插入）都会让后面全部失效**。

一句话结论：**上下文优化的本质是"保持前缀稳定 + 提高单位 token 的信息密度"**，不是"塞得更多"。

### 4.2 六条实战经验（Manus，均可在 10 篇看原文）

| 经验 | 具体做法 | 为什么 |
|---|---|---|
| 稳定前缀 | 系统提示/工具定义固定在前，动态内容追加在后 | 缓存按前缀匹配，前段一变全废 |
| append-only | 不改写历史消息，只追加 | 改写 = 缓存失效 + 模型认知被打断 |
| mask 而非 remove | 不用的工具/上下文做屏蔽，不物理删除 | 删除会移动后续位置，破坏缓存 |
| 文件系统当外存 | 中间产物写文件，需要时再读 | 上下文只留"指针 + 结论" |
| todo.md 复述 | 每轮把当前任务清单重述一遍 | 长任务里防目标漂移，成本极低 |
| 避免 few-shot rut | 少量多样示例，避免固定模板化输出 | 过度 few-shot 会让模型机械模仿 |

附加两条同样重要：**保留错误信息**（错误是重要信号，不要为了"干净"清理掉）、**每个任务开始前重置无关上下文**（比在脏上下文里挣扎更省）。

### 4.3 长任务的三种策略（按成本/保真排序）

| 策略 | 做法 | 适合 | 代价 |
|---|---|---|---|
| Compaction | 到阈值时摘要历史，保留最近文件访问记录（Anthropic 的 compaction 保留最近 5 个文件） | 单线长任务 | 摘要损失细节，需可回溯原文 |
| 笔记外置 | 关键决策/事实写文件，上下文只留索引 | 需要长期保持一致的工程任务 | 要维护笔记结构 |
| 子代理隔离 | 大量阅读/探索交给 subagent，只回收 1,000–2,000 token 结论 | 探索型、并行调研 | token 总量上升（但主上下文干净） |

> 注意：三者不是替代关系。成熟系统通常是"子代理读 → 主上下文留结论 → 阈值到了 compaction → 跨会话靠笔记"。

### 4.4 缓存契约（工程细节，最容易踩坑）

- 最小可缓存前缀通常有下限（Bedrock 文档口径：512–4,096 tokens，视模型而定），短提示无法缓存；
- 缓存有 TTL（5 分钟 / 1 小时两档），**空闲超过 TTL 就重新计费**——所以"每隔几分钟戳一下"比"放一小时再回来"更贵；
- 失效顺序：**tools → system → messages**，工具定义变动代价最大（所以工具集顺序要稳定，动态工具要放在后面或用 mask）；
- 时间戳/随机 ID/当前时间这类内容**永远不要放在前缀里**（这是最常见的缓存杀手）。

### 4.5 token 指标（怎么算"使用率高"）

不要把"少 token"当目标，看这四个：

| 指标 | 定义 | 健康方向 |
|---|---|---|
| **每成功任务 token** | 总 token / 通过验证的任务数 | ↓（唯一真正的效率指标） |
| **缓存命中率** | cached_tokens / input_tokens | ↑（>60% 说明前缀设计合理） |
| **输入输出比** | input / output | 生产级 agent 常见 100:1 量级；异常高说明在读太多无关内容 |
| **读完率 / 冗余率** | 工具返回中被后续引用的比例 | ↑；低说明返回太啰嗦 |

## 5. 杠杆 D：编排与模型——拆不拆、拆多细、交什么

> 细节见 `12-multiagent.md`（判据/拓扑/handoff）、`13-model-prompt-memory.md`（提示词/推理预算/记忆）。

### 5.1 多智能体：先证明必要，再动手

**收益证据**：Anthropic 内部研究评测上，多 agent（Orchestrator + 子代理）比单 agent Claude Opus 4 **+90.2%**。
**成本证据**：多 agent 系统 token 消耗约为 chat 的 **~15×**（chat 本身约 4×）；Anthropic 归因"token 使用量本身解释了 80% 的方差"。

**所以判据是：只有当"上下文隔离、并行探索、审查独立性"带来的收益 > 15× token 成本时才拆。**

| 该拆 | 不该拆 |
|---|---|
| 任务可切成低耦合子任务，且需要大量独立探索 | 子任务强耦合、需要共享隐式上下文 |
| 需要并行（多文件/多方案/多数据源） | 单线程顺序推理即可 |
| 需要独立审查（不同模型家族交叉评审） | 只是"想显得更忙" |
| 主上下文已接近 attention 极限 | 任务本身 3–5 步就能完成 |

**五条"不要用"硬信号**（12 篇 §1）：单个 agent 加工具能做完；子任务之间要频繁交换中间状态；错误归因需要跨 agent 追踪而你还没有 trace；预算敏感（15×）；你还没有验证闭环（并行会放大错误）。

### 5.2 五种拓扑与各自失败模式

| 拓扑 | 结构 | 典型失败 | 对策 |
|---|---|---|---|
| 单 agent + 工具 | 一个循环调工具 | 长任务目标漂移 | todo 复述 + 定期重述目标 |
| Orchestrator–Worker | 主分派、子执行 | 主上下文被回传淹没 | 子只回 1–2k token 结构化摘要 |
| Pipeline | 固定阶段串联 | 阶段间契约不清、错误静默传递 | 每阶段显式 schema + 门禁 |
| 递归规划 | planner 可再 spawn subplanner | 深度爆炸、层级失效 | 限制深度（如 ≤3）、每层必须产出可验证切片 |
| 群聊 / 自协调 | 共享状态互相协商 | **锁竞争**（Cursor 实测 20 agents 退化到 1–3 的吞吐） | 结构化分工 + 单一写者，避免共享状态协商 |

### 5.3 拆解粒度的经验值（Anthropic 原文口径）

- 1 个 agent：3–10 次工具调用；
- 2–4 个子代理：每个 10–15 次工具调用；
- >10 个子代理：必须明确分工，否则重复劳动；
- 想要"多铺开"时给**数量区间**："Generate 20–100 tasks" 比 "generate many tasks" 有效得多。

### 5.4 Handoff 契约：报告不是"我完成了"

12 篇给了 12 字段模板，最小可用六项：

```markdown
- objective      接到的目标（原文，不改写）
- done           做了什么（文件/命令/提交，可核对）
- evidence       证据（输出片段/退出码/diff/截图路径）
- deviations     偏离计划之处及原因   ← 最常被省略，也最有价值
- concerns       已知风险/未验证假设
- next           建议下一步（或明确"已完结"）
```

Cursor 的 worker 报告七类（what was done / notes / concerns / deviations / findings / thoughts / feedback），核心也是"偏离与风险必须显式"。

### 5.5 并发与深度控制

- 并发上限（如 8）+ 队列，**不要靠自然限流**（否则出现"全员抢小任务、大任务没人做"）；
- 深度上限（如 ≤3）+ 每层明确"我负责的切片边界"；
- 长任务配合后台 job：前台只等数秒，超出转后台并定期查（否则一次卡死吃掉整个上下文窗口）；
- **只让最终报告结束任务**（子代理"我看完了"不算完成）——这与 dsh-superagent 的"只有 report 能关工单"是同一设计。

## 6. 模型、提示词与记忆——最便宜的三处调整

> 细节见 `13-model-prompt-memory.md`（10 节，含可直接抄的 prompt 骨架与 thinking 档位表）。

### 6.1 提示词五区结构（固定顺序，便于缓存）

```
1 role        你是谁、边界在哪（越短越好）
2 background  任务背景/领域约束（只写模型无法从环境发现的东西）
3 instructions 要做什么（意图 + 验收条件，不是步骤清单）
4 tool guidance 何时用哪个工具、何时不要用
5 output      输出格式 + 验收标准（可机判）
```

铁律：**能通过读仓库/读环境得到的信息，不要写进提示词**（会腐化，且占缓存前缀）。经验值：项目级常驻上下文 < 200 行。

### 6.2 推理预算（thinking）

| 档 | 何时用 | 预算量级 |
|---|---|---|
| L0 不开 | 格式转换、简单检索、模板填充 | 0 |
| L1 轻 | 常规代码修改、单文件重构 | ~1k |
| L2 中 | 多文件改动、调试、方案权衡 | ~4k |
| L3 重 | 架构决策、疑难 bug、多方案比较 | 16k+ |

硬约束（extended thinking 文档口径）：最小预算 1,024 tokens；`budget_tokens < max_tokens`；预算 > 32K 时建议用 batch；`max_tokens > 21,333` 必须开 streaming。
取舍：thinking 与缓存/温度/强制工具调用存在冲突，**把预算当旋钮做 A/B（1k vs 4k vs 16k），别凭感觉设**。

### 6.3 记忆三层

| 层 | 载体 | 存什么 | 不要存什么 |
|---|---|---|---|
| 工作记忆 | 当前上下文 | 当前任务状态、最近证据 | 历史全量日志 |
| 会话记忆 | compaction 摘要 + 决策笔记 | 已定决策、被否决方案及理由 | 可重读的代码细节 |
| 跨会话语义记忆 | MEMORY 索引 + 文件（每条带 id/source/confidence/scope/expires） | 稳定事实、教训、约定 | 时效性强的临时状态 |

**经验固化（ACE 的思路）**：把"重复出现的纠正"沉淀成增量 bullet（带 helpful/harmful 计数），而**不是整体重写系统提示**——整体重写在实证中会导致 context collapse（ACE 论文里第 60 步上下文从 18,282 tokens 塌缩到 122 tokens，分数从 66.7 掉到 57.1；采用增量演化后 agents +10.6%、finance +8.6%、AppWorld 最高 +17.1%、适配延迟 −86.9%）。

## 7. 一套度量：不测就无法调优

| 层级 | 指标 | 定义 | 反模式 |
|---|---|---|---|
| 任务 | **pass@1** | 一次成功比例（按 feature 验证判定） | 用"看起来对"当通过 |
| 任务 | pass@k | k 次内成功比例（衡量稳定性） | 只看最好一次 |
| 成本 | 每成功任务 token | 总 token / 通过数 | 只看单价，不看返工 |
| 工具 | tool_errors / 任务 | 工具调用失败次数 | 把工具错误算成模型错误 |
| 过程 | 每任务工具调用数 | 衡量路径长度 | 越少越好是误解（复杂任务该多） |
| 质量 | 返工率 / revert 率 | 合入后需修的比例 | 只看合入速度 |
| 上下文 | 缓存命中率 | cached / input | 只看总 token |

**方法论要点**：

- **失败归因用"五抽屉"**：任务理解错 / 环境或工具错 / 上下文缺失 / 模型能力不足 / 验证缺失。归错抽屉 = 优化错方向。
- **A/B 时每轮只改一个变量，跑 ≥5 次看方差**（agent 输出方差很大，n=1 的结论基本无效）。
- **trace 要能 replay**：四层留痕（输入、工具调用与原始返回、模型输出、判定结果），否则你无法在不重跑 LLM 的情况下复现失败。
- 跨版本比较要小心：任务集、模型、工具集任一变化都会让历史基线失效。
- 业界参考基线（一手）：SWE-bench 2,294 题 / 12 个 Python 仓库，论文期最强模型仅解 1.96%（说明"真实仓库任务"非常难，别拿玩具任务当能力证明）；CodeRabbit review 接受率 36.4%、讨论 7.3%、拒绝 56.3%。

## 8. 落地清单：30 / 60 / 90 天

### 第 1–30 天：零风险、纯工程（不看模型也能获益）

- [ ] 给 3–5 个核心功能写 Feature Map（四段），跑通"一个命令验真假"
- [ ] 工具返回裁剪 + 长结果分页 + 错误结构化（`error_code/retry_with/hint`）
- [ ] 加硬边界：危险命令拒绝、路径/schema 校验、提交前 lint 拦 TODO/调试残留
- [ ] 上下文前缀稳定化：固定系统提示与工具顺序，动态内容一律后置，前缀里清掉时间戳/UUID
- [ ] 建立 trace 四层留痕 + 至少一条可 replay 的失败样例

### 第 31–60 天：把"验证"和"度量"变成日常

- [ ] 验证技能治理：frontmatter（owner/last_verified/stability）、14 天审计队列、基线变更人工 review
- [ ] 任务集 20–50 条（来自真实失败案例），四指标同报（pass@1 / pass@k / cost / tool_errors）
- [ ] 失败五抽屉归因表，每周复盘一次
- [ ] 项目常驻上下文瘦身到 < 200 行，重复叮嘱 2 次以上的规则下沉到 lint/CI/hook
- [ ] thinking 档位 A/B：同一任务集跑 1k / 4k / 16k，定出默认档

### 第 61–90 天：引入编排与长时任务

- [ ] 只读探索用子代理隔离（主上下文只留结论），记录 token 与质量变化
- [ ] Handoff 六字段模板上线，子任务报告缺 deviations/concerns 视为未完成
- [ ] 低风险、完成条件可机验的任务开 Overnight Run（六要素：覆盖等待/可验证完成条件/隔离 worktree/不问人/写清卡点/循环）
- [ ] 跨模型家族评审试点（评审者 ≠ 作者），驳回必须附理由
- [ ] 建立"每成功任务 token"看板，把优化从感觉变成曲线

## 10. 反模式 Top 12（跨六篇汇总）

1. 用"测试通过/编译通过"当完成证据。
2. 用长篇计划制造"正在推进"的错觉（计划长度 ≠ 证据强度）。
3. 在提示词里写本可以用 schema/lint 消灭的约束。
4. 每次纠正都加一句提示词，提示词膨胀到没人敢改。
5. 上下文塞满再说"模型记不住"（应外置/压缩/隔离）。
6. 前缀里放时间戳、随机 ID、动态工具列表 → 缓存全灭。
7. 用 n=1 的对比判断优化有效。
8. 多智能体并行跑一个还没验证闭环的任务（并行放大错误）。
9. 子代理回传全文而非结论（主上下文被淹没）。
10. 用共享状态自协调并发 agent（锁竞争把 20 个压到 1–3 个的吞吐）。
11. 让 agent 自己更新验证基线（假绿）。
12. 只优化单价不看返工（每成功任务成本才是效率）。

## 11. 争议与未决（诚实标注）

| 议题 | 现状 | 我们的判断 |
|---|---|---|
