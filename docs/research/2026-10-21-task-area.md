# 任务区调研：面向智能体长任务的对话与汇总

- 调研时间：2026-10-21
- 基线版本：`d.21.1.6.0`（HITL 规则记忆、拒绝语义、自我修改回滚、Wiki 来源、视觉附件已合入）
- 交付版本：`d.22.1.6.0`（任务区首版）
- 上游材料：`docs/research/2026-10-20-competitive-analysis-v2.md`、`docs/research/2026-10-21-feature-parity-and-optimization.md`
- 复用口径：**只借鉴产品交互与数据模型，未复制任何第三方代码**；Claude Code 为闭源商业产品，仅阅读公开文档与使用观察。

---

## 0. 结论先行

1. **"任务"不是新的聊天类型，而是对话外面的一层记录。** Codex、Claude Code、Cline、Roo Code 的共同点是：执行仍发生在同一条会话里，任务层只负责**目标、状态、步骤、结果**四件事。和鸣因此没有新增一套消息协议，而是复用现有 `conversationId + streamId`，把运行事件旁路记到本机任务档。
2. **汇总必须确定性生成，不能交给模型再总结一遍。** 模型总结会引入二次幻觉，也无法解释"为什么是失败"。和鸣的报告完全由任务记录拼装（状态、耗时、步骤、拒绝原因、来源），同一份记录每次生成逐字相同，可直接进审计/复盘。
3. **"重新执行"是任务区最被低估的能力。** Aider 的 `/undo`、Cline 的任务历史、Roo Code 的子任务回退都说明：长任务失败后，用户要的是**带着原目标重来**，而不是重新打一遍提示词。和鸣的 `reopen + 重新投递` 保住了原始目标与智能体，同时新开一条流。
4. **持久化边界必须是本机。** 任务记录含工具参数、文件内容与执行结果，这些正是和鸣"数据不出设备"承诺里最敏感的部分。任务档只写 localStorage，不上云、不进 E2E 消息；云端仍只看到普通聊天消息。
5. **不做全自动循环。** 没有"允许全部"档，没有无人值守的自主重试。每个工具调用仍走 HITL 闸门；任务区只是把闸门之后发生的事记录下来，不改变闸门本身的判定。

## 2. 横向对照

### 2.1 任务如何被组织

| 产品 | 组织单位 | 与对话的关系 | 状态表达 |
|---|---|---|---|
| Codex | 任务/线程 | 一个任务对应一次执行上下文 | 排队、执行中、完成、失败 |
| Claude Code | 当前会话 + 待办清单 | 待办挂在会话内，逐项勾选 | 待办项 pending / in_progress / completed |
| opencode | 会话 | 会话即任务，消息内嵌工具轨迹 | 流式、完成、错误 |
| Cline | 任务历史条目 | 每个任务独立目录，可回看 | 执行中、完成、取消 |
| Roo Code | 父任务 + 子任务 | 父任务派发子任务，结果回流 | 父/子各自状态 |
| 和鸣任务区 | 任务记录（本机） | 复用一条 `agent` 会话，任务只是旁路记录 | running / done / failed / cancelled |

**结论**：任务层的价值在"索引"和"收口"，不在于另起一套执行引擎。和鸣保留单会话执行，避免出现"任务状态"和"聊天消息"两套真相。

### 2.2 汇总信息从哪里来

| 产品 | 汇总来源 | 风险 |
|---|---|---|
| Codex | 执行结果 + 变更摘要 | 摘要由模型生成，可能漏步骤 |
| Claude Code | 待办清单 + 最终回复 | 待办是模型自报，未必覆盖真实工具调用 |
| Cline | 工具调用记录 + 最终回复 | 记录完整，但展示依赖 UI 状态 |
| 和鸣任务区 | `onToolTrace` + `onRunSettled` 的**结构化事件** | 只记录真实发生的事；无模型二次总结 |

**结论**：和鸣的步骤来自编排层的工具轨迹回调，而不是模型自述。模型说"我改好了"不算数，`stepEnd(ok)` 才算数；被 HITL 拒绝的步骤单独标 `denied`，不会混成"失败"。

### 2.3 失败与重试

| 产品 | 失败后的动作 |
|---|---|
| Codex | 保留任务，可重新发起 |
| Claude Code | 会话内继续对话，或 `--resume` 恢复 |
| Cline | 任务历史中重开 |
| Roo Code | 子任务失败回到父任务 |
| Aider | `/undo` 回退最近一次变更 |
| 和鸣任务区 | `reopen` 后带原目标重新投递；旧步骤清空，新流新记录 |

和鸣没有做自动重试：自动重试会在用户不知情时重复执行写操作，与 HITL 的"每次写都要问"直接冲突。重试必须是用户显式动作。

## 3. 采纳的设计

### 3.1 数据模型

```
TaskRecord
  id, conversationId, agentId, agentName
  title, prompt
  status: running | done | failed | cancelled
  createdAt, updatedAt, endedAt?
  streamId?
  result?, error?
  steps: TaskStep[]

TaskStep
  id, name, args
  status: running | ok | error | denied
  result?, startedAt, endedAt?
  sources?: ToolSource[]
  denyCause?: "user" | "rule" | "gate"
```

- `status` 只有四态，不给"暂停/排队"等需要调度器的状态——和鸣没有后台队列，多出来的状态只会说谎。
- `denyCause` 直接复用 HITL 的拒绝原因，报告里能区分"用户当场拒绝 / 命中记住的规则 / 确认流程异常"。
- `sources` 来自工具执行结果，Wiki 类任务的来源因此能进报告。

### 3.2 收口时机

`onRunSettled(streamId, { status, finalText?, error? })` 是**恰好一次**的终结回调：

- 正常完成 → `ok`
- 用户中断 / AbortError → `aborted`
- 供应商报错、读取历史失败、未绑定 LLM → `error`

它独立于 `onTurnComplete`：后者在没有正文时可能不触发，任务会永远停在 running。收口回调放在 `finally` 语义里，任何提前返回都必须先 settle。

### 3.3 页面结构

```
┌ 任务列表 280px ┬ 嵌入式对话（复用 ChatPage） ┬ 确定性汇总 320px ┐
│ 搜索 / 筛选    │ 消息、流式、工具轨迹、HITL  │ 状态、目标、结果 │
│ 状态徽标       │ 与普通会话完全一致          │ 步骤、来源、报告 │
└────────────────┴────────────────────────────┴──────────────────┘
```

- 对话区直接 `ChatPage embedded`，不复制输入栏与消息渲染，避免两套 E2E/附件/HITL 逻辑漂移。
- 汇总区不做"AI 再总结"，只渲染结构化字段；复制按钮输出 Markdown，便于贴进 issue 或周报。
- 新建任务时自动选中唯一已绑定智能体；未绑定的智能体在选项里禁用并给出原因。

### 3.4 容量与陈旧

| 约束 | 值 | 原因 |
|---|---|---|
| 任务数 | 60 | localStorage 单键可控，超出裁最旧 |
| 单任务步骤 | 40 | 防止工具循环把记录撑爆 |
| 标题 / 目标 | 60 / 4000 字符 | 标题用于列表，目标保留完整意图 |
| 结果 / 单步结果 | 12000 / 1600 字符 | 报告可读，避免整份文件入库 |
| 任务档总字节 | ~1.1 MB | 接近 localStorage 配额时仍留出消息缓存空间 |
| 陈旧判定 | 10 分钟无更新 | 应用崩溃/强退后，下次启动把 running 收口为 failed |

## 4. 明确不采纳

| 做法 | 不采纳原因 |
|---|---|
| 全局 auto-approve / "允许全部" | 与 HITL 红线冲突；任务区不改变闸门 |
| 模型生成任务总结 | 二次幻觉、不可复现；报告必须是记录的纯函数 |
| 任务记录上云 | 含工具参数、文件内容；违反"数据不出设备" |
| 自动重试写操作 | 用户不知情时重复执行，风险高于收益 |
| 后台任务队列/调度器 | 当前是桌面单机执行，引入队列会制造"假状态" |
| 复制上游任务面板代码 | 许可证虽多为宽松，但 UI 与数据模型强绑定，复制成本高于自写 |

## 6. 后续可做（未进本版）

1. **任务模板**：把常用的"排查构建失败 / 生成周报"存成模板，新建时预填目标与智能体。
2. **跨会话来源聚合**：同一任务引用多个 Wiki 页面时，汇总区按来源去重并分组。
3. **任务级导出**：除 Markdown 外支持导出 JSON，便于外部审计；仍保持本机生成。
4. **子任务**：借鉴 Roo Code 的父子任务，但需要先解决"父任务如何汇总子任务收口"的一致性，暂缓。
