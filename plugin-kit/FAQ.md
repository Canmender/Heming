# 插件常见问题（FAQ）

> 按「作者最常卡住」排序。契约细节见 [STANDARD.md](STANDARD.md)，操作步骤见 [AUTHORING.md](AUTHORING.md)。
> 报错文案请先用 `pnpm plugin:lint` 复现——它与安装预览是同一套权威校验。

---

## 清单与字段

**Q1：`id` 发布后还能改吗？**
不能。`id` 是安装身份：同 id 再装 = 更新，换 id = 用户那儿多一个插件（旧的还在）。发布前想清楚，建议反向域名或 `作者.能力`。

**Q2：`version` 有什么规则？**
自由字符串（≤32 字），建议 semver。**同一 id + 同一 version 的内容不可变**——改了内容必须升版本，否则服务端 409 拒绝。草稿阶段随便改，发布后就要升。

**Q3：`engines.heming` 写多少？**
写**你真正需要的最低宿主版本**，如 `d.117`。写太高会把老用户挡在门外；写低了但用了新字段，用户会「能装但不生效」。只支持「最低版本」语义，不支持 `^`/`~` 区间。

**Q4：顶层多写一个字段会怎样？**
不阻断：解析器**剥掉并给 warning**（「已忽略未知字段 X」）。但 `permissions` / `meta` / 每个贡献条目是 **strict**：写错位置会直接报错——这是为了不让权限类笔误被静默忽略。

**Q5：`$schema` 是干什么的？会不会被拒？**
只给编辑器补全用，解析器**已知并忽略**，不会告警。它的值可以是仓库内相对路径或 https URL。

**Q6：为什么编辑器按 schema 不报错，装的时候却失败？**
JSON Schema 只描述形状，**不表达跨字段规则**（bundle 组合、MCP host 必须被 `permissions.network` 覆盖、工具名不得跨束重复…）。权威校验永远是 `parsePluginManifestV5` / `plugin-lint` / 安装预览。

## 权限

**Q7：为什么提示「permissions.network 未覆盖 MCP 服务主机 X」？**
每个 `mcpServers[].url` 的 host（含非默认端口）都必须写进 `permissions.network`。只写 `host` 或 `host:port`，不要写 `https://`、路径、通配符；默认端口（443/80）两侧会统一，可以不写。

**Q8：`tools: "write"` 是不是模型就能随便写了？**
不是。`tools` 只是**风险上限**：`read` 时写工具不注入，`write` 时允许注入但**每次写操作仍走人工确认**。权限只收紧执行面，不放宽 HITL。

**Q9：`permissions.events` 声明了就能收到事件吗？**
声明是前提，不是保证：事件还受宿主状态影响（主窗前台时 notify 被抑制、窗口隐藏时丢弃、生命周期不重放）。而且**未声明的类型一条都收不到**。

**Q10：`files` 权限为什么像没生效？**
当前版本只校验与展示（预留），不授予文件工具。这也是「插件不执行代码」的一部分。

## 安装与生效

**Q11：插件装了，但智能体不用它？**
按顺序查：① 插件总开关是不是关的；② 该技能是否被**分配**给这个智能体（技能池可单独分配）；③ 技能/贡献级开关；④ 插件详情「诊断」看阻断原因（停用/依赖/兼容/签名/超权限/孤儿）。不要靠猜。

**Q12：诊断说「兼容性不满足」是什么意思？**
`engines.heming` 比当前宿主新（需要更新和鸣），或清单写了非法版本号（包的问题）。前者升级应用，后者改清单。

**Q13：为什么安装完 MCP 服务显示未连接、工具是关的？**
安全设计：插件安装**不自动连接、不自动授权**。用户要在接口区连接服务，再逐个开启工具（工具可能有副作用）。插件作者应在 README 里写清这一步。

**Q14：更新插件会丢掉用户的设置吗？**
不会：按技能名/服务 key 原地更新，保留接口区补的请求头、工具启用状态、贡献级停用选择与安装时间。**权限变宽**时会要求用户重新确认。

**Q15：卸载会删数据吗？**
声明式插件卸载只收回它物化的技能/服务/命令与记录，不动其它数据。界面插件的 `data/` 随插件删除；`settings.json` 在「保留设置」时保留。

## 界面插件（首方）

**Q16：第三方能发布带界面的插件吗？**
不能。bundle 等于「装插件即在本机运行代码」，只对首方签名开放；正式版忽略所有 `dev-*` 公钥。第三方要做界面，正确路径是先把能力做成声明式包。

**Q17：bundle 为什么 lint 说「打包前模式」？**
打包/签名之前 `packageSha256` 还不存在，lint 用 `dev` 模式放行（格式给了仍严格校验）；签名后由打包脚本写入并在安装口径重算比对。

**Q18：界面插件里能用 localStorage 吗？**
不要用：独立 origin 下不可靠（清缓存/崩溃即丢）。偏好走 `settings()`，业务数据走 `data*`（JSON、单文件 ≤1MB、卸载即删）。

**Q19：为什么拿不到窗口坐标、也不能自由缩放？**
刻意设计：位移由主进程按屏幕光标计算，缩放只能按清单 `scales[]` 逐档 ±1。插件做拖拽时**只发信号**，不要自己算坐标。

**Q20：`chatConfig()` 返回为什么没有提示词/密钥？**
`permissions.chat: true` 只给本机网关 origin 与智能体 `{id,name}`；人设 `prompt` 与用户供应商 Key **永不下发**。这是审计后的硬边界。

## 工具链与发布

**Q21：`plugin-lint` 报「找不到 packages/shared/dist/index.js」？**
先 `pnpm --filter @heming/shared build`（或直接用 `pnpm plugin:check`，它会先构建）。

**Q22：`pnpm plugin:check` 会校验模板吗？**
不会：它校验 `plugins/` 与 `plugin-kit/examples/`，跳过 `_invalid` 与模板（模板里有 `{{id}}` 占位符，本就不是合法清单）。

**Q23：示例里的 `_invalid/demo-bad` 为什么故意写错？**
用来演示校验器怎么点名错误（缺 `engines`、host 未声明），并保证错误提示不会退化。别抄它。

**Q24：插件应该放在仓库哪里？**
```
plugins/<目录>/plugin.json        # 真实要发布/安装的包
plugin-kit/examples/<目录>/       # 示例（不发布）
```
`plugins/` 下带 `plugin.json` 的目录会被测试逐一校验（能解析、不含代码/密钥）。

**Q25：改完清单要跑什么？**
`pnpm plugin:lint`（单包也可 `node scripts/plugin-lint.mjs <目录>`）→ 应用里安装预览 → 发布前 `pnpm plugin:check`。
改了 shared 的清单字段才需要 `pnpm plugin:schema` 重新生成编辑器 schema（`plugin:check` 会挡漂移）。
